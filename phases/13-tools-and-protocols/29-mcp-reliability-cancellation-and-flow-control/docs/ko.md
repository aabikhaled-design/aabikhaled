# MCP의 신뢰성과 취소, 흐름 제어 (MCP Reliability, Cancellation, and Flow Control)

> 요청 식별자는 메시지를 서로 짝지어 줄 뿐이다. 그것이 부수 효과를 안전하게 만들어 주지도, 작업자를 멈춰 주지도, 느린 소비자로부터 스트림을 지켜 주지도 않는다.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13, Lessons 09 and 13
**Time:** ~120 minutes

## 학습 목표 (Learning Objectives)

- stdio와 Streamable HTTP 각각에 맞는 취소 신호를 구현한다.
- 완료와 취소가 겹치는 경쟁을 해소하되, 취소 뒤에 메시지를 보내지 않는다.
- 요청 취소와 오래 남는 `tasks/cancel`의 의미를 구분한다.
- 부수 효과와 명시적인 멱등성 키를 근거로 재시도 여부를 판단한다.
- 최종 응답은 지키면서 진행 알림 대기열에 한도를 둔다.
- 다시 연결하고, 다시 가져오고, 간격에 무작위를 섞어 물러나며 스트림을 회복한다.

## 문제 (The Problem)

정상 경로는 분산 시스템에서 가장 비싼 결함을 가린다.

클라이언트가 도구를 부른다. 서버가 작업을 시작한다. 진행 알림이 도착한다. 프록시가 스트림을 버퍼에 담아 둔다. 클라이언트가 제한 시간에 걸려 연결을 끊는다. 서버는 1밀리초 뒤에 작업을 마친다. 클라이언트는 새 JSON-RPC 식별자로 다시 시도한다. 그 변경 작업이 두 번 실행된다.

구성 요소는 저마다 국소적으로는 올바르게 동작했다. 그런데 시스템 전체는 실패했다.

MCP는 메시지와 전송 동작을 정의하지만, 다음은 여전히 애플리케이션의 몫이다.

- 시간 예산.
- 업무 차원의 멱등성.
- 한도가 걸린 대기열.
- 재시도 분류.
- 오래 남는 태스크 상태.
- 다시 연결하고 다시 가져오는 정책.

이 레슨은 그 판단들을 결정적으로 동작하는 시뮬레이터에 담아 만든다.
잠들기도, 소켓도, 무작위 실패도 없다. 취소 사건의 순서를 직접
정할 수 있다. 동기화된 스레드 테스트 하나가 원장 클라이언트 둘을
같은 멱등성 키에 대해 경쟁시킨다.

## 요청 취소는 전송 계층마다 다르다 (Request Cancellation Is Transport-Specific)

의도는 어느 전송 계층에서나 같다. 클라이언트가 진행 중인 결과를 더 이상 필요로 하지 않는다는 것이다. 다만 실제로 오가는 신호가 다르다.

### stdio

stdio는 양방향 채널 하나를 함께 쓴다. 클라이언트는 알림을 보낸다.

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

이 알림은 보내고 잊는다. 서버는 여기에 JSON-RPC 응답을 내지 않는다.

서버는 작업을 멈추고, 자원을 풀고, 그 요청에 대한 응답을 보내지 않아야 한다. 모르는 요청이거나 이미 끝났거나 안전하게 멈출 수 없는 요청이라면 취소를 무시해도 된다.

형식이 잘못되었거나 모르는 요청이거나 이미 완료된 요청에 대한 취소 알림은 무시한다. 그런 경쟁 상황을 새 오류로 바꾸면 경쟁만 더 늘어난다.

### Streamable HTTP

요즘의 Streamable HTTP는 요청마다 자기 HTTP 응답이나 SSE 응답 스트림을 갖는다. 클라이언트는 그 요청의 응답 스트림을 닫아서 취소한다.

평범한 HTTP 요청에 `notifications/cancelled`를 POST하지 마라. 스트림을 닫는 것이 곧 취소 신호다.

서버는 연결이 끊긴 것을 알아차리는 즉시 작업을 멈춰야 하고, 그 요청에 대해 더 이상 메시지를 보내서는 안 된다.

### 서버가 보내는 취소는 범위가 좁다

서버는 클라이언트의 아무 호출이나 취소하려고 `notifications/cancelled`를 쓰지 않는다. stdio에서 서버가 보내는 취소는 `subscriptions/listen` 요청을 끝내는 데에만 쓴다. 그 경로를 평범한 클라이언트 요청 취소와 섞지 마라.

## 취소는 경쟁이다 (Cancellation Is a Race)

두 가지 사건 순서 모두 유효하다.

### 취소가 이기는 경우

```text
request starts
client sends cancellation signal
server marks request cancelled
worker reaches completion
server suppresses the response
```

### 완료가 이기는 경우

```text
request starts
worker commits the result
server sends the response
cancellation arrives late
server ignores the late notification
```

클라이언트도 이미 포기한 요청에 늦게 도착한 응답을 무시해야 한다. 네트워크 지연 때문에, 어느 쪽도 상대가 어떤 사건을 먼저 봤는지 증명할 수 없다.

```figure
mcp-reliability-race
```

이 레슨의 `RequestCoordinator`는 최종 상태를 하나만 저장한다. 취소된 뒤에는 `complete()`가 응답을 돌려주지 않는다. 늦게 도착한 취소는 이미 완료된 기록을 바꾸지 못한다.

## 제한 시간에는 시계가 둘 필요하다 (Timeouts Need Two Clocks)

아무 활동이 없을 때만 재는 타이머 하나로는 부족하다.

한도를 둘 두어라.

1. **유휴 제한 시간.** 그 요청이 쓸모 있는 활동 없이 얼마나 있을 수 있는지.
2. **최대 제한 시간.** 요청이 시작된 때부터 재는 절대적인 시간 예산.

진행 알림은 유휴 시계를 되돌릴 수 있다. 그러나 최대 기한을 없앨 수는 없다.

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

1500밀리초 시점에서 이 요청은 아직 살아 있다. 가장 최근 진행 알림이 300밀리초밖에 안 되었기 때문이다. 2000밀리초에서는 1999밀리초에 진행 알림이 왔더라도 최대 기한이 그 요청을 취소한다.

진행 알림은 선택이다. 서버는 진행 토큰을 받고도 아무 알림을 내지 않을 수 있다. 토큰이 있다는 사실을 무한 대기로 바꾸지 마라.

MCP의 진행 값은 반드시 커져야 한다. 완료되거나 취소된 뒤에는 알림이 멈춘다. 빠른 작업자가 전송 계층을 넘치게 하지 않도록 진행 알림에 호출 한도를 두어라.

## 요청 취소는 `tasks/cancel`이 아니다 (Request Cancellation Is Not `tasks/cancel`)

이 둘은 서로 다른 수명을 다룬다.

| 장치 | 대상 | 신호 | 성공이 뜻하는 것 |
|-----------|--------|--------|--------------------|
| stdio의 요청 취소 | 진행 중인 RPC 하나 | `notifications/cancelled` | 클라이언트가 그 요청을 포기했으니 가능하면 서버도 멈춰야 한다 |
| HTTP의 요청 취소 | 진행 중인 응답 스트림 하나 | 스트림을 닫는다 | 클라이언트가 그 요청을 포기했으니 가능하면 서버도 멈춰야 한다 |
| `tasks/cancel` | 오래 남는 태스크 하나 | 평범한 MCP 요청 | 서버가 취소 의사를 접수했다 |

`tasks/cancel`이 성공했다고 해서 작업자가 멈췄다는 증명이 되지는 않는다. 작업자가 다음 점검 지점에서 그 표시를 볼 때까지 그 태스크는 `working` 상태로 남을 수 있다. 그 점검 지점에 닿기 전에 작업이 끝나 버릴 수도 있다.

HTTP 연결이 끊겼다고 해서 오래 남는 태스크 상태를 지우지 마라. 애초에 태스크를 만든 이유가, 그 수명이 요청 하나와 연결 하나보다 오래 간다는 데 있다.

## 새 JSON-RPC 식별자는 멱등성이 아니다 (A New JSON-RPC ID Is Not Idempotency)

JSON-RPC 식별자는 요청과 응답을 짝지어 줄 뿐이다. 업무상의 연산을 식별하지는 않는다.

클라이언트가 식별자 `41`로 결제를 보냈다가 응답을 잃고 식별자 `42`로 다시 시도했다고 하자. 서버는 서로 다른 메시지 두 개를 본다. 애플리케이션 차원의 키가 없으면, 그 둘이 하나의 결제를 뜻한다는 것을 알 수 없다.

멱등성 키는 그 업무상의 의도를 식별한다.

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

서버는 다음을 저장한다.

- 그 키.
- 연산 인자의 지문 값.
- 확정된 결과.

같은 키에 같은 인자면 저장해 둔 결과를 돌려준다. 같은 키인데 인자가 다르면 물리친다. 그래야 키를 실수로 다시 쓰는 일이 다른 업무 연산을 바꿔 버리지 않는다.

### 원장 경계는 원자적이고 오래 남아야 한다

다음 순서는 안전하지 않다.

```text
check key
run mutation
store result
```

작업자 둘이 모두 키가 없다고 관측하고 둘 다 변경 작업을 실행할 수 있다.
효과가 일어난 뒤 저장하기 전에 죽으면, 재시도할 때 같은 모호함이 생긴다.

이 레슨은 파일에 저장되는 SQLite 원장을 쓴다. `BEGIN IMMEDIATE`가 키 확인과
흉내 낸 업무 효과, 실행 횟수 세기, 결과 저장을 하나의 트랜잭션으로 묶어 준다.
그래서 서로 독립적인 원장 연결 둘이 같은 키로 경쟁해도, 확정된 결과는 하나이고
실행도 한 번이다. 원장을 닫았다
다시 열어도 그 기록은 남아 있다.

돌려주는 값은 모두 저장된 JSON에서 다시 만든다. 호출자는 원장이 들고 있는
변경 가능한 객체를 결코 받지 않으므로, 돌려받은 딕셔너리를 고쳐도 이후의
재생 결과가 망가지지 않는다.

시뮬레이터에서 말하는 업무 효과는 같은 SQLite 트랜잭션 안의 영수증과 실행
횟수다. 실제 결제나 배포, 외부 API 호출은 로컬 테이블에 기록한다고 해서
원자적이 되지 않는다. 실무에는 공유되는 내구성 있는 데이터베이스 트랜잭션이나
트랜잭션 아웃박스, 또는 같은 멱등성 키를 강제해 주는 상위 공급자가 필요하다.
프로세스 잠금 하나로는 복제본 여럿을
보호하지 못하고 재시작도 견디지 못한다.

### 재시도 판단 표

구현하기 전에 재시도를 분류하라.

| 갈래 | 예 | 재시도 규칙 |
|------|---------|------------|
| 안전 | 부수 효과가 없는 결정적인 읽기 | 어디에서 실패했는지 파악한 뒤 새 JSON-RPC 식별자로 다시 시도한다 |
| 조건부 | 오래 남는 멱등성 키가 붙은 변경 작업 | 같은 키와 똑같은 인자로 다시 시도한다 |
| 위험 | 업무 차원의 중복 제거가 없는 변경 작업 | 자동으로 재시도하지 말고 먼저 대조해서 맞춘다 |

`readOnlyHint`나 `idempotentHint` 같은 도구 주석은 여전히 믿을 수 없는 힌트다. 재시도해도 되는지는 애플리케이션 계약과 서버 구현이 정한다.

## 역압은 정확성의 일부다 (Backpressure Is Part of Correctness)

SSE 생산자는 클라이언트나 프록시, 네트워크가 소비할 수 있는 속도보다 빠르게 진행 알림을 만들어 낼 수 있다. 한도 없는 대기열은 느림을 메모리 고갈로 바꿔 놓는다.

한도를 건 대기열을 쓰고, 무엇을 잃어도 되는지 정하라.

진행 알림은 대체할 수 있다. 같은 토큰이라면 나중 진행 값이 앞선 값을 대신한다. 최종 JSON-RPC 응답은 대체할 수 없다.

이 레슨의 버퍼는 다음 정책을 적용한다.

1. 같은 토큰에 대해 이어지는 진행 알림을 하나로 합친다.
2. 용량이 차면 가장 오래된 진행 알림을 버린다.
3. 그 스트림에 대해 정본을 다시 가져와야 한다고 표시한다.
4. 최종 응답은 지킨다.
5. 최종 응답을 지키려고 다른 최종 응답을 버려야 하는 상태는 아예 거부한다.

이것이 명시적인 회복 경로를 갖춘, 한도 있는 손실이다. 조용한 손실은 전략이 아니다.

### 프록시 버퍼링

서버는 제대로 스트리밍하는데 역방향 프록시가 이벤트를 버퍼에 붙들고 있을 수 있다.

SSE 응답에는 다음을 보내라.

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026년 Streamable HTTP 명세는 호환되는 프록시가 이벤트를 곧바로 전달하도록 `X-Accel-Buffering: no`를 권한다.

오래 열려 있으면서 조용한 스트림에는 SSE 주석을 주기적으로 내보내라.

```text
:
```

클라이언트는 주석 줄을 무시한다. 중간 장비는 통신이 오가는 것을 보게 되어, 놀고 있는 연결이라고 끊을 가능성이 줄어든다.

연결 유지 신호는 진행 알림이 아니다. 전송 계층의 주석이 하나 도착했다고 해서 그 연산의 의미상 유휴 제한 시간을 되돌리지 마라.

## 다시 연결한다는 것은 다시 가져온다는 뜻이다 (Reconnect Means Refetch)

요즘의 Streamable HTTP는 `Last-Event-ID`로 SSE를 이어 받는 것을 지원하지 않는다.

`subscriptions/listen` 스트림이 끊긴 뒤에는 이렇게 하라.

1. 새 JSON-RPC 식별자로 새 listen 요청을 연다.
2. 원하던 구독 조건을 복원한다.
3. 영향을 받은 도구와 자원, 프롬프트, 태스크를 정본 메서드로 다시 가져온다.
4. 안정된 식별자로 애플리케이션 상태의 중복을 제거한다.
5. 응답을 잃었다는 이유만으로 위험한 변경 작업을 다시 실행하지 않는다.

예제의 회복 계획은 `sendLastEventId`를 명시적으로 거짓으로 두고, 다시 가져올 자원을 나열한다.

### 다시 연결이 한꺼번에 몰리는 것을 막아라

클라이언트 1만 개가 정확히 1초 뒤에 한꺼번에 다시 연결하면, 회복 중인 서버가 다시 쓰러진다.

지수적으로 물러나되 무작위를 섞고 상한을 두어라. 이 레슨은 테스트를 재현할 수 있도록, 클라이언트 식별자와 시도 횟수에서 결정적으로 무작위 값을 계산한다.

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

실무에서는 암호학적으로 안전한 난수나 실행 환경의 난수를 쓸 수 있다. 지켜야 할 것은 특정 수식이 아니라 값이 흩어지게 만드는 것이다.

## 직접 만들기 (Build It)

`code/main.py`에서 신뢰성과 관련된 작은 구성 요소 다섯 개를 만든다.

### `RequestCoordinator`

- 유휴 기한과 최대 기한을 두고 진행 중인 요청을 시작한다.
- 값이 커지는 진행 알림을 내보낸다.
- stdio나 HTTP에 맞는 취소 신호를 만들어 낸다.
- 유효하지 않은 취소 알림을 무시한다.
- 취소와 완료 사이의 최종 상태 경쟁을 눈에 보이게 만든다.
- 서버가 보내는 취소는 stdio 구독에만 쓴다.

### `MutationLedger`

- 업무 키가 없으면 JSON-RPC 식별자 두 개가 두 번 실행된다는 것을 보여 준다.
- 키 확인과 흉내 낸 효과, 실행 횟수, 결과
  저장에 파일 기반 SQLite 트랜잭션을 쓴다.
- 서로 독립적인 원장 연결에 걸쳐, 하나의
  멱등성 키와 같은 인자에 대해 중복을 제거한다.
- 같은 키에 다른 인자가 오면 물리친다.
- 방어적인 사본을 돌려주고, 다시 열어도 확정된 기록을 지킨다.

### `DurableTaskService`

- 취소 요청을 접수한다.
- 작업자가 점검 지점에 닿을 때까지 태스크를 `working`으로 둔다.
- 접수가 최종 상태가 아닌 이유를 보여 준다.

### `BoundedSseBuffer`

- 압박이 있을 때 진행 알림을 합치거나 버린다.
- 정본을 다시 가져와야 한다는 사실을 기록한다.
- 최종 응답은 절대 버리지 않는다.

### 회복 보조 함수

- 프록시에 안전한 SSE 헤더와 연결 유지 주석을 돌려준다.
- 다시 연결하고 다시 가져오는 계획을 만든다.
- 결정적인 지수 물러남과 무작위 섞기로 재시도를 흩뜨린다.

## 직접 해 보는 실습 (Interactive Lab)

잠들기 없이 사건 순서 네 가지를 돌려 보라.

1. 요청 `A`를 시작하고, 취소한 다음, `complete()`를 부른다.
2. 요청 `B`를 시작하고, 완료한 다음, 취소를 전달한다.
3. 요청 `C`를 시작하고, 유휴 기한이 올 때마다 진행 알림을 내다가, 최대 기한을 넘긴다.
4. 요청 `D`를 Streamable HTTP로 시작하고 그 응답 스트림을 닫는다.

각 상황마다 다음을 기록하라.

- 요청의 최종 상태.
- 최종 응답이 존재하는지.
- 실제로 통신에 실린 취소 신호.
- 클라이언트가 무시해야 하는 사건이 무엇인지.

그다음 `D`를 stdio로 바꿔라. 연산은 똑같지만 취소 신호는 달라져야 한다.

## 연습 실습 (Practice Lab)

`MutationLedger`에 `reserve_inventory` 변경 작업을 추가하라.

요구 사항은 이렇다.

1. 키가 SKU와 수량, 테넌트, 연산 이름에 묶인다.
2. 같은 키와 같은 인자로 재시도하면 첫 번째 예약을 돌려준다.
3. 수량이 바뀐 채로 재시도하면 예약을 또 만들지 않고 실패한다.
4. 확정은 되었는데 응답을 잃은 실행을 키로 대조해서 맞출 수 있다.
5. 결과에 비밀 값이나 결제 데이터를 남기지 않는다.
6. 클라이언트가 키를 주지 않았다면 자동 재시도를 끈다.
7. 구독이 끊기는 상황을 흉내 내고, 다음에 무엇을 할지 정하기 전에 재고 기록을 다시 가져온다.
8. 원장 연결 두 개를 같은 출발점에서 시작해 같은 키를 동시에 보낸다.
   예약이 하나만 확정되었는지 단언한다.
9. 처음 돌려받은 예약 객체를 고쳐 본다. 그 키를 다시 재생해서 저장된 결과가
   바뀌지 않았음을 증명한다.
10. 원장 파일을 닫았다 다시 열고, 그 키로 예약을 대조해서 맞춘다.

실습을 정직하게 유지하라. 재고가 다른 서비스에 있다면,
그 서비스가 같은 멱등성 키를 받아들이는지 아니면 트랜잭션 아웃박스가
로컬 확정을 원격 효과로 이어 주는지 설명하라.

## 확인하기 (Verify It)

다음 문장이 모두 참일 때 이 레슨이 끝난 것이다.

- stdio 취소는 `notifications/cancelled`를 보내고 응답을 받지 않는다.
- Streamable HTTP 취소는 요청 스트림을 닫고 취소 POST를 보내지 않는다.
- 완료 전에 취소하면 최종 응답이 나가지 않는다.
- 취소 전에 완료하면 응답이 남고 늦은 취소는 무시된다.
- 진행 알림이 유휴 제한 시간은 되돌리지만 최대 제한 시간은 되돌리지 못한다.
- JSON-RPC 식별자만 새로 주면 변경 작업이 다시 실행된다.
- 멱등성 키 하나와 같은 인자면, 연결 두
  개가 동시에 경쟁해도 한 번만 실행된다.
- 확정된 기록은 다시 열어도 남아 있고, 재생하면 방어적인 사본을 돌려준다.
- 돌려받은 결과 하나를 고쳐도 저장된 결과는 바뀌지 않는다.
- 한도가 걸린 버퍼가 용량 안에 머물면서 최종 응답을 지킨다.
- 다시 연결할 때 새 요청을 쓰고, `Last-Event-ID`를 보내지 않고, 영향받은 상태를 다시 가져온다.
- `tasks/cancel` 접수 뒤에도, 작업자가 그것을 관측하기 전까지 태스크는 최종 상태가 아니다.

## 실무에서 겪는 실패 양상 (Production Failure Modes)

| 실패 | 겉으로 드러나는 증상 | 올바른 대응 |
|---------|--------------------|------------------|
| HTTP 클라이언트가 취소 알림을 POST한다 | 서버와 클라이언트가 요청 수명에 대해 서로 다르게 안다 | 그 요청의 SSE 응답 스트림을 닫는다 |
| 취소를 받아들인 뒤에도 서버가 응답한다 | 클라이언트가 쓸 수 없는 늦은 결과를 받는다 | 취소가 이겼다면 작업을 멈추고 이후 메시지를 내지 않는다 |
| 진행 알림이 모든 기한을 되돌린다 | 멈춰 버린 작업이 영원히 살아남는다 | 절대적인 최대 제한 시간을 따로 둔다 |
| 새 RPC 식별자를 중복 제거로 여긴다 | 결제나 배포, 삭제가 두 번 실행된다 | 오래 남는 애플리케이션 멱등성 키를 더한다 |
| 키 확인과 효과가 따로 논다 | 동시에 도는 작업자 둘이 모두 키가 없다고 본다 | 키 선점과 효과 기록, 결과를 한 번에 확정한다 |
| 메모리 원장을 복제본에 걸쳐 쓴다 | 재시작하거나 다른 작업자가 앞선 확정을 잊는다 | 공유되는 내구성 저장소나 상위 공급자의 멱등성을 쓴다 |
| 저장된 변경 가능한 결과를 그대로 돌려준다 | 호출자가 그것을 고쳐서 이후 재생을 망친다 | 확정된 결과를 직렬화하고 방어적인 사본을 돌려준다 |
| 같은 키를 다른 인자로 다시 쓴다 | 키 하나가 서로 다른 업무 의도 둘을 가리킨다 | 인자의 지문 값을 저장하고 비교한다 |
| 진행 알림 대기열에 한도가 없다 | 소비자가 느리면 메모리가 계속 늘어난다 | 한도 안에서 대체 가능한 진행 알림을 합치고 버린다 |
| 압박 속에서 최종 응답을 버린다 | 클라이언트가 요청 결과를 알 길이 없다 | 용량을 미리 떼어 두거나 진행 알림을 버리되 최종 응답은 지킨다 |
| 프록시가 SSE를 버퍼에 담는다 | 진행 알림이 몰아서 오거나 제한 시간이 지난 뒤에 온다 | 버퍼링을 끄고 호환되는 프록시 제한 시간을 설정한다 |
| `Last-Event-ID`가 된다고 가정한다 | 서버가 지원하지 않는 지점에서 이어 받으려 한다 | 새 요청으로 다시 연결하고 상태를 다시 가져온다 |
| 모든 클라이언트가 즉시 다시 연결한다 | 회복 과정이 또 다른 장애를 만든다 | 상한을 둔 지수 물러남에 무작위를 섞는다 |
| 태스크 접수를 최종 취소로 여긴다 | 화면에는 멈췄다고 나오는데 작업자는 계속 돈다 | 최종 상태가 될 때까지 태스크를 확인한다 |

## 캡스톤과의 연결 (Capstone Connection)

도구 생태계 캡스톤은 신뢰성을 구조도 속의 문단이 아니라 실행 가능한 근거로 다뤄야 한다.

다음 산출물을 요구하라.

- 전송 계층마다의 취소 경쟁 기록 하나씩.
- 노출된 변경 작업마다의 재시도 표.
- 멱등성 키 기록과 인자가 어긋나는 고정 데이터.
- 같은 키를 동시에 보낸 기록, 다시 열었을 때의 확인, 반환 객체 변경 검사.
- 한도가 걸린 버퍼를 넘치게 한 결과.
- 역방향 프록시용 SSE 헤더와 유휴 정책.
- 정본을 다시 가져오는 메서드를 밝힌 재연결 계획.
- 캡스톤이 태스크를 쓴다면 오래 남는 태스크의 취소 기록.

로컬 프로세스에서 요청 하나가 초록색이 되는 것은 정상 경로만 증명한다. 잃어버린 응답과 늦은 취소, 느린 소비자, 한꺼번에 몰리는 재연결에 대해 결과가 정해져 있을 때 그 캡스톤이 실무에 쓸 만해진다.

## 핵심 용어 (Key Terms)

| 용어 | 뜻 |
|------|---------|
| Request cancellation | 진행 중인 MCP 요청 하나를 포기하는 것 |
| Cancellation race | 최종 완료와 취소 사건이 서로 겨루는 상황 |
| Idle timeout | 마지막으로 쓸모 있는 요청 활동이 있었던 뒤로 재는 한도 |
| Maximum timeout | 요청 시작부터 재는 절대 한도이며 진행 알림에 영향받지 않는다 |
| Idempotency key | 업무상의 의도 하나를 중복 제거하는 애플리케이션 식별자 |
| Atomic ledger | 키 선점과 효과 기록, 결과를 한 단위로 확정하는 내구성 있는 경계 |
| Backpressure | 생산자가 소비자보다 빠를 때 거는 통제 |
| Progress coalescing | 앞선 진행 값을 더 새로운 정본 값으로 대체하는 것 |
| Refetch | 스트림이 끊긴 뒤 현재 상태를 다시 읽어 오는 것 |
| Jitter | 재시도를 시간상 흩뜨리기 위해 일부러 넣는 변동 |
