# MCP 도구 계약과 콘텐츠 (MCP Tool Contracts and Content)

> 도구를 자동으로 부르는 것이 안전해지는 때는, 탐색과 인자, 결과, 페이지 나누기, 전송 메타데이터가 하나의 계약 위에서 서로 어긋나지 않을 때뿐이다.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13, Lessons 07, 09, and 10
**Time:** ~120 minutes

## 학습 목표 (Learning Objectives)

- JSON Schema 2020-12로 도구의 입력과 출력을 정의한다.
- 구조화된 결과가 JSON 객체라고 가정하지 않고 검증한다.
- 텍스트와 이미지, 오디오, 자원 링크, 내장 자원 가운데 알맞은 것을 고른다.
- 안전하지 않은 `x-mcp-header` 정의를, 그 도구가 모델에 닿기 전에 물리친다.
- 파라미터 헤더 값을 인코딩하고 헤더와 본문이 정확히 일치하는지 확인한다.
- 커서 값을 해석하지 않으면서 커서 페이지 나누기를 따라간다.
- `completion/complete`가 내놓는 제안에 한도를 두고 권한을 확인한다.

## 문제 (The Problem)

Python 함수를 부르는 것은 쉽다. AI 호스트를 거쳐 원격 기능을 부르는 것은 계약의 문제다.

서버는 기술자를 공개한다. 클라이언트는 그것을 모델 맥락과 사용자 인터페이스로 옮긴다. 모델은 인자를 만든다. 게이트웨이가 그 요청을, 복사된 헤더를 보고 어디론가 보낼 수도 있다. 서버는 도구를 실행한다. 그다음 클라이언트가 그 결과를 모델에 돌려줘도 될 만큼 안전하고 유효한지 판단한다.

경계 하나만 약해도 이 사슬 전체가 망가진다.

다음 다섯 가지 실패를 보라.

- 기술자는 결과가 객체라고 말하는데 서버는 배열을 돌려준다.
- `nextCursor`가 빈 문자열일 때 클라이언트가 페이지 나누기를 멈춘다.
- 토큰 파라미터가 HTTP 헤더로 복사되어 중간 장비에 노출된다.
- 유니코드가 들어간 라우팅 값이 날것의 헤더로 전송되고, 게이트웨이와 원본 서버가 서로 다른 바이트를 해석한다.
- 완성 제안 엔드포인트가, 접근할 수 없는 호출자에게 운영 환경을 제안한다.

이 가운데 어느 것도 프롬프트를 잘 써서 고칠 수 없다. 명시적인 프로토콜 계약과 애플리케이션 계약이 있어야 한다.

## 계약 파이프라인 (The Contract Pipeline)

도구 호출을 다섯 개의 관문으로 다뤄라.

1. **탐색.** 결과가 일정하고 페이지가 나뉜 도구 목록을 읽는다.
2. **승인.** 기술자마다 검증하고 로컬 보안 정책을 적용한다.
3. **호출.** 인자를 검증하고 전송 메타데이터를 만든다.
4. **실행.** 핸들러를 돌리고 실패를 올바른 갈래로 분류한다.
5. **소비.** 모델이 쓰기 전에 콘텐츠 블록과 구조화된 출력을 검증한다.

```figure
mcp-contract-pipeline
```

승인 관문과 소비 관문은 호스트의 몫이다. 서버는 자기 주석이나 스키마, 출력을 믿으라고 클라이언트에 강요할 수 없다.

## JSON Schema는 실행 시점의 경계다 (JSON Schema Is a Runtime Boundary)

MCP `2026-07-28`에서 `inputSchema`와 `outputSchema`는 JSON Schema를 쓴다. `$schema`가 없으면 기본 방언은 2020-12다.

입력 스키마는 스키마 객체여야 한다. 인자가 없는 도구라도 무엇을 받아들이는지 정확히 밝혀야 한다.

```json
{
  "type": "object",
  "additionalProperties": false
}
```

이것은 임의의 속성을 받아들이는 `{ "type": "object" }`보다 엄격하다.

출력 스키마는 선택이다. 다만 서버가 그것을 한 번 공개하면, 완료된 모든 도구 결과는
그 스키마에 맞는 `structuredContent`를 돌려주겠다고 약속하는 것이 된다.
`isError: true`인 결과도 마찬가지다. 오류 표시는 실행 결과를 분류할 뿐,
공개한 출력 계약을 면제해 주지 않는다. 클라이언트는 기술자를 믿는 대신
결과를 직접 검증해야 한다.

### 구조화된 콘텐츠는 어떤 JSON 값도 될 수 있다

`structuredContent`를 딕셔너리로 못 박지 마라. 다음 어느 것이든 될 수 있다.

- 객체.
- 배열.
- 문자열.
- 숫자.
- 참·거짓 값.
- `null`.

다음 도구는 배열을 돌려준다.

```json
{
  "name": "tag_catalog",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false
  },
  "outputSchema": {
    "type": "array",
    "items": {"type": "string"}
  }
}
```

그 성공 결과는 이렇게 유효하다.

```json
{
  "resultType": "complete",
  "content": [
    {
      "type": "text",
      "text": "[\"contracts\", \"mcp\", \"stateless\"]"
    }
  ],
  "structuredContent": ["contracts", "mcp", "stateless"],
  "isError": false
}
```

호환을 위해, 구조화된 결과에는 직렬화된 JSON을 텍스트 블록에도 담아야 한다. 다만 검증의 근거는 그 텍스트가 아니라 `structuredContent`다.

### 작은 검증기로도 경계를 가르칠 수 있다

이 레슨은 Python 표준 라이브러리 안에 머물기 위해 JSON Schema의 일부만 일부러 구현한다. 예제 도구들이 실제로 쓰는 장치만 확인한다.

- object와 array, string, integer, number, boolean, null 타입.
- 필수 속성.
- `additionalProperties: false`.
- 배열의 요소 타입.
- 열거된 값.
- 문자열 최소 길이.

이것은 실무용 검증기를 대신하지 못한다. 여기에서 다시 쓸 만한 교훈은 검증이 어디에서 일어나야 하는지다. 기술자는 탐색 뒤에, 인자는 실행 전에, 구조화된 결과는 소비 전에 검증한다.

## 콘텐츠 블록마다 치르는 비용이 다르다 (Content Blocks Carry Different Costs)

`content` 배열에는 여러 콘텐츠 유형을 함께 담을 수 있다.

| 유형 | 쓰는 곳 | 주된 경계 |
|------|------------|---------------|
| `text` | 사람과 모델이 읽는 요약 | 텍스트를 믿을 수 없는 출력으로 다룬다 |
| `image` | base64로 인코딩한 시각 근거 | 미디어 타입과 크기를 검증한다 |
| `audio` | base64로 인코딩한 음성이나 녹음 | 미디어 타입과 길이 한도를 검증한다 |
| `resource_link` | 클라이언트가 나중에 가져올 수 있는 URI | 나중의 자원 읽기에 다시 권한을 확인한다 |
| `resource` | 결과에 직접 담은 데이터 | 지금 바로 크기와 내용 한도를 강제한다 |

자원 링크가 있다고 해서 그 자원이 `resources/list`에 나온다는 증명은 되지 않는다. 그것은 이번 도구 호출이 돌려준 참조일 뿐이다. 클라이언트는 그 URI를 따라갈 때 여전히 자기 자원 정책을 적용한다.

내장 자원을 쓰면 왕복을 한 번 줄이지만 지금 응답의 크기가 커진다. 크거나 따로 바뀌는 산출물에는 링크를 쓰라. 결과와 함께 반드시 한 덩어리로 움직여야 하는 작은 근거에는 내장 자원을 쓰라.

이 레슨의 `evidence_bundle` 결과에는 다섯 유형이 모두 들어 있다. 클라이언트는 결과를 받아들이기 전에 블록마다 검증한다.

## `x-mcp-header`는 라우팅 메타데이터다 (`x-mcp-header` Is Routing Metadata)

`inputSchema` 안의 속성은 `x-mcp-header`를 선언할 수 있다. Streamable HTTP에서는 클라이언트가 그 인자를 `Mcp-Param-{name}`으로 복사해 보낸다.

```json
{
  "region": {
    "type": "string",
    "x-mcp-header": "Region"
  }
}
```

`region: "eu-west"`라면 전송 계층은 이렇게 내보낼 수 있다.

```http
Mcp-Param-Region: eu-west
```

이 주석이 있는 이유는 로드 밸런서나 게이트웨이, 정책 엔진이 JSON 본문을 파싱하지 않고도 요청을 보낼 곳을 정할 수 있게 하기 위해서다. 자격 증명을 넣는 자리가 아니다.

프로토콜은 이 주석을 다음과 같이 제약한다.

- 헤더 이름은 비어 있지 않고 HTTP 필드 이름 토큰 문법을 따른다.
- 헤더 이름은 대소문자를 무시하고 봐도 서로 겹치지 않는다.
- 속성 타입은 string, integer, boolean이다.
- `number`는 허용되지 않는다.
- 이 주석은 `inputSchema.properties`의 직접 구성원에만 붙는다.
- 정수 값은 `-9007199254740991`에서 `9007199254740991` 사이에 머문다.

위치 규칙은 문법에 따른 것이며 애매하면 물리치는 쪽으로 동작한다. 검증기가 아는 속성만이
아니라 스키마 나무 전체를 훑어라. 중첩된 객체의 `properties` 아래나 `oneOf` 분기,
`items`, `$ref`로 닿는 정의, 또는 출력 스키마에 붙은 주석은 물리쳐라. 참조를 해석한다고 해서
그 대상이 최상위 직접
속성이 되지는 않는다.

이 레슨은 배포 정책을 하나 더한다. `password`나 `secret`, `token`, `api_key`, `authorization` 같은 이름을 복사하는 기술자를 물리치는 것이다. 공식 명세는 서버 작성자에게 민감한 파라미터를 복사하지 말라고 권한다. 클라이언트는 그 권고를 확정적인 승인 규칙으로 바꿀 수 있다.

헤더의 값이 아니라 이름을 기록하라. 예제 코드는 `Mcp-Param-Region`은 남기고 `eu-west`는 감사 기록에서 뺀다.

### HTTP 헤더를 만들기 전에 값을 인코딩하라

파라미터 값이 그대로 실려도 되는 경우는, 그것이 비어 있지 않은 문자열이면서
`!`부터 `~`까지의 보이는 ASCII 문자로만 이루어져 있고 인코딩 표식과 닮지 않았을 때뿐이다.
그 밖의 모든 값은 정확히 다음 형식을 쓴다.

```text
=?base64?{Base64UTF8}?=
```

`Base64UTF8`은 그 값의 정확한 UTF-8 바이트에 대한 표준 base64다. 먼저 다듬거나
정규화하거나 치환하지 마라. 유니코드와 빈 문자열, 공백, 탭, 제어 문자,
CR이나 LF, 앞뒤 공백, 그리고 `=?base64?`로 시작하는 값은 모두 인코딩하라.
표식처럼 보이는 값을 한 번 더 인코딩해야, 받는 쪽이 그것을 전송 문법으로 해석하지 않고
원래 글자 그대로
되살릴 수 있다.

참·거짓 값은 소문자 `true`나 `false`로 적는다. 정수는 10진수로 적고
JavaScript 안전 정수 범위 안에 있어야 한다. 그 범위를 벗어난 값은 중간 장비가
반올림하지 않고 물리친다.

### 서버가 복사된 사본을 검사한다

헤더를 만드는 것은 클라이언트 쪽 절반일 뿐이다. Streamable HTTP 경계에서
서버는 다음을 해야 한다.

1. 인식하는 `Mcp-Param-*` 이름을, 대소문자를 무시하고 찾아낸다.
2. base64 표식 형식이 있으면 정확히 해독한다.
3. 해독한 텍스트를 JSON 본문의 대응 인자와 정확히 비교한다.
4. 인식하는 헤더가 없거나 중복되거나 예상 밖이거나 형식이 잘못되었거나 값이 맞지 않으면,
   처리에 넘기기 전에 물리친다.

물리칠 때는 HTTP `400`과 JSON-RPC 오류 코드 `-32020`을 쓴다. 본문 값도,
그것을 인코딩한 헤더 형태도 감사 기록에 넣지 마라. 인식한 헤더 이름과
물리친 이유의 갈래만 기록하라.

`code/main.py`가 이 경계를 그대로 모델링한다. [09번 레슨](../../09-mcp-transports/)은
메서드와 프로토콜 판본 일치를 포함해 더 넓은 Streamable HTTP 검증
순서를 다룬다.

## 페이지 커서는 속을 들여다보지 않는다 (Pagination Cursors Are Opaque)

MCP의 목록 연산은 커서 페이지 나누기를 쓴다. 페이지 크기와 커서 형식은 서버가 정한다. 클라이언트가 내리는 판단은 하나뿐이다.

```python
if result.get("nextCursor") is None:
    break
cursor = result["nextCursor"]
```

이렇게 쓰지 마라.

```python
if not result.get("nextCursor"):
    break
```

빈 문자열도 유효한 커서다. 참·거짓으로 판단하면 너무 일찍 멈춘다.

클라이언트는 커서를 해독하거나, 값을 올리거나, 앞선 커서와 크기를 비교하거나, 페이지 번호를 짐작해서는 안 된다. 서버는 커서에 서명을 붙이거나, 카탈로그 판본에 묶거나, 내부 상태에 대응시킬 수 있다. 그것은 서버의 구현 사정이다.

예제 서버는 첫 페이지 뒤에 일부러 `""`를 돌려준다. 클라이언트는 두 번째 요청에 그 값을 그대로 실어 보내야 한다. 그 기록은 이렇다.

```text
<first request with no cursor>
<second request with cursor "">
```

유효하지 않은 커서는 JSON-RPC의 잘못된 파라미터 오류인 코드 `-32602`를 낸다.

## 완성 제안은 권한 확인 지점이다 (Completion Is an Authorization Surface)

`completion/complete`는 프롬프트 인자와 자원 템플릿 인자에 대한 제안을 준다. 대화형 입력 화면에는 쓸모가 있지만, 평범한 목록 메서드가 감춰 주던 이름이 새어 나갈 수 있다.

완성 요청은 참조 대상과 지금 완성하려는 인자를 밝힌다.

```json
{
  "method": "completion/complete",
  "params": {
    "ref": {
      "type": "ref/prompt",
      "name": "deployment_review"
    },
    "argument": {
      "name": "environment",
      "value": "st"
    }
  }
}
```

결과는 값을 최대 100개까지 돌려주며 `total`과 `hasMore`를 함께 알려 줄 수 있다.

참조 대상인 프롬프트나 자원이 쓰는 것과 같은 권한 경계를 적용하라. 예제에서 분석가는 `development`와 `staging`을 받는다. `production`은 운영자만 받을 수 있다.

실무의 완성 제안에는 다음도 필요하다.

- 입력 검증.
- 호출자에 따른 걸러 내기.
- 클라이언트 쪽의 요청 억제.
- 서버 쪽의 호출 한도.
- 결과 개수의 상한.
- 민감한 제안 값을 드러내지 않는 로그.

완성 제안은 입력을 돕는 기능이지 탐색을 우회하는 통로가 아니다.

## 오류 계층은 둘이다 (Two Error Layers)

프로토콜 오류와 도구 실행 오류를 나눠라.

MCP 요청 자체를 제대로 처리할 수 없을 때는 JSON-RPC 오류를 쓴다.

- 모르는 도구 이름.
- 형식이 잘못된 요청.
- 빠진 요청 메타데이터.
- 유효하지 않은 커서.

호출이 도구에 닿았고 그 도구가 조치할 수 있는 실패를 알릴 때는 `isError: true`인 완료된 도구 결과를 쓴다.

- 보고서 원본을 쓸 수 없다.
- 날짜가 지원 범위를 벗어났다.
- 업무 규칙이 그 요청을 물리쳤다.

모델은 도구 실행 오류라면 대개 스스로 고쳐 볼 수 있다. 그러나 서버가 자기 출력 스키마를 어긴 경우는 고칠 수 없다.

도구가 출력 스키마를 선언했다면, 조치할 수 있는 실패도 그 스키마 안에서 표현하라.
예제의 `route_report` 실패는 요청받은 지역을 `accepted: false`와 함께 돌려주고,
사람이 읽는 오류 문구와 `isError: true`를 나란히 둔다.

## 직접 만들기 (Build It)

`code/main.py`가 Python 표준 라이브러리만으로 경계의 양쪽을 모두 만든다.

서버는 다음을 구현한다.

- 요청마다의 MCP 메타데이터 검증.
- 도구와 완성 제안 기능을 알리는 `server/discover`.
- 결과가 일정한 `tools/list` 페이지 나누기.
- 물리쳐야 할 것 하나를 포함한 도구 기술자 네 개.
- 배열 형태의 구조화된 출력.
- 현재 정의된 모든 도구 콘텐츠 블록 유형.
- 인식한 파라미터 헤더를 해독하고, 값이 어긋나면 HTTP `400`과 JSON-RPC `-32020`을
  돌려주는 Streamable HTTP 일치 검사 관문.
- 권한을 확인하고 호출 한도를 둔 완성 제안.

클라이언트는 다음을 구현한다.

- 기술자 승인.
- 스키마 나무 전체에 대한 `x-mcp-header` 위치 검증과 민감 필드 정책.
- 보이는 ASCII를 그대로 쓰거나 base64 UTF-8로 정확히 인코딩하는 값 처리.
- 빈 문자열도 따라가는, 속을 들여다보지 않는 커서 루프.
- 인자와 결과 검증.
- 콘텐츠 블록 검증.
- 값은 빼고 이름만 담은 헤더 감사 기록.

일부러 안전하지 않게 만든 기술자는 가르치기 위한 데이터다. 그것 하나를 물리쳐도 나머지 유효한 도구들이 정상적으로 올라온다는 것을 보여 준다.

그리고 호출자에 따라 걸러진 완성 제안 값을 출력한다.

## 직접 해 보는 실습 (Interactive Lab)

`code/main.py`를 열고 `TOOLS`를 찾아라.

1. `tag_catalog.outputSchema.type`을 `array`에서 `object`로 바꿔라.
2. 데모를 돌려라. 클라이언트가 돌아온 배열을 물리쳐야 한다.
3. 스키마를 되돌려라.
4. 첫 페이지의 `nextCursor`는 `""`로 두고, 마지막 페이지가 필드를 빼는 대신
   `nextCursor: None`을 돌려주게 하라.
5. 테스트를 돌리고 커서 기록을 비교하라.
6. 문자열 속성에 `x-mcp-header: "Authorization"`을 추가하라.
7. 기술자 승인 단계에서 호출 전에 그것을 물리치는지 확인하라.
8. `region` 값으로 유니코드와 줄바꿈, 앞뒤 공백이 있는 문자열, 그리고
   `=?base64?SGVsbG8=?=`라는 글자 그대로의 텍스트를 시험하라. 내보낸 헤더를 각각 해독해서
   원래 값이 정확히 살아남는지 증명하라.
9. 그 주석을 `oneOf`나 `items`, `$ref` 정의 아래로 옮겨라. 데모가 그 분기를 쓰지 않더라도
   기술자가 물리쳐지는지 확인하라.
10. 인식하는 헤더를 지우거나 해독된 값을 바꿔라. HTTP 경계가 상태 `400`과
    JSON-RPC 코드 `-32020`을 돌려주는지 확인하라.

여기에서 노리는 것은 JSON의 모양을 외우는 것이 아니다. 각 관문이 자기가 맡은 경계에서 실패하는 모습을 직접 보는 것이다.

## 연습 실습 (Practice Lab)

계약 실습에 `search_evidence` 도구를 추가해서 확장하라.

요구 사항은 이렇다.

1. 입력 스키마가 `query`와 `limit`, 그리고 안전한 `region` 라우팅 필드를 받는다.
2. 출력 스키마는 `uri`와 `title`, `score`를 가진 객체의 배열이다.
3. 결과에는 호환용 텍스트와 항목마다의 자원 링크가 들어간다.
4. 인자는 정의되지 않은 속성을 물리친다.
5. `limit`은 애플리케이션 검증으로 상한을 둔다.
6. 어떤 URI에 접근 권한이 없는 호출자는 완성 제안이나 도구 출력을 통해서도 그 URI를 보지 못한다.
7. 테스트에는 스키마에 맞지 않는 점수와 잘못된 헤더 주석, 두 페이지짜리 목록이 들어간다.
8. 헤더 값 테스트는 보이는 ASCII와 유니코드, 제어 문자, 공백,
   표식처럼 보이는 텍스트, 그리고 JavaScript 안전 정수의 양쪽 경계를 모두 다룬다.
9. HTTP 고정 데이터는 헤더 이름의 대소문자를 가리지 않고 받아들이되, 인식하는 값이 없거나
   맞지 않으면 상태 `400`과 코드 `-32020`으로 물리친다.

## 확인하기 (Verify It)

다음 문장이 모두 참일 때 이 레슨이 끝난 것이다.

- `tools/list`가 되풀이 호출에서 같은 논리 순서를 돌려준다.
- `nextCursor`가 `""`일 때 클라이언트가 두 번째 요청을 보낸다.
- 민감한 헤더를 복사하는 안전하지 않은 기술자가 빠지고, 다른 도구는 그대로 쓸 수 있다.
- 배열이 자기 배열 출력 스키마를 통과한다.
- 객체가 그 같은 배열 스키마에서 실패한다.
- 오류 결과도 공개된 출력 스키마를 빼먹거나 어길 수 없다.
- 텍스트와 이미지, 오디오, 자원 링크, 내장 자원 블록이 모두 검증을 통과한다.
- 헤더 감사 기록에 이름은 있고 값은 없다.
- 보이는 ASCII는 그대로 남고, 유니코드와 제어 문자, 공백이 붙은 값, 빈 값,
  표식처럼 보이는 값은 정확한 base64 UTF-8 인코딩을 거쳐 원래대로 되돌아온다.
- JavaScript 안전 범위를 벗어난 정수를 복사하려 하면 물리친다.
- `oneOf`와 `items`, 중첩 객체, `$ref` 정의, 출력 스키마 아래의 주석은
  승인 단계에서 물리친다.
- 대소문자를 가리지 않고 인식한 헤더는 해독된 값이 본문과 정확히 같을 때만 통과하고,
없거나 맞지 않으면 HTTP
`400`과 JSON-RPC `-32020`을 낸다.
- 분석가에게는 완성 제안이 `production`을 절대 돌려주지 않는다.
- 도구 실패에는 `isError: true`를 쓰고, 형식이 잘못된 프로토콜 호출에는 JSON-RPC `error`를 쓴다.

## 실무에서 겪는 실패 양상 (Production Failure Modes)

| 실패 | 학습자가 보게 되는 것 | 올바른 대응 |
|---------|-----------------------|------------------|
| 클라이언트가 출력을 객체로 가정한다 | 유효한 배열이 실패하거나 조용히 감싸진다 | 객체만 허용하는 타입 없이, 공개된 스키마로 검증한다 |
| 빈 커서를 거짓으로 다룬다 | 마지막 페이지들이 사라진다 | `nextCursor`가 있고 null이 아니면 계속 진행한다 |
| 민감한 값을 복사한다 | 비밀 값이 프록시나 방화벽, 추적 데이터에 나타난다 | 그 기술자를 물리치고 비밀 값은 보호되는 요청 데이터에 둔다 |
| 유니코드나 공백을 날것으로 복사한다 | 게이트웨이와 원본 서버의 해석이 어긋나거나 값이 정규화된다 | 정확한 base64 UTF-8 표식 인코딩을 쓰고 해독한 뒤에 비교한다 |
| 주석이 스키마 분기에 숨어 있다 | 클라이언트가 승인 단계에서 라우팅 메타데이터를 놓친다 | 스키마 나무 전체를 훑고 최상위 직접 속성만 허용한다 |
| 큰 정수를 복사한다 | JavaScript 중간 장비가 라우팅 값을 반올림한다 | JavaScript 안전 정수 범위를 벗어난 값을 물리친다 |
| 헤더와 본문이 어긋난다 | 게이트웨이가 보낸 대상과 원본 서버가 실행한 대상이 다르다 | 처리에 넘기기 전에 HTTP `400`과 JSON-RPC `-32020`으로 물리친다 |
| 출력 스키마를 무시한다 | 이후 코드가 망가진 구조를 소비한다 | 모델이나 애플리케이션이 쓰기 전에 검증한다 |
| 자원 링크를 그냥 믿는다 | 호출자가 권한 없는 URI를 따라간다 | 자원 읽기마다 권한을 다시 확인한다 |
| 완성 제안이 전역 목록을 공유한다 | 감춰야 할 테넌트 이름이 새어 나간다 | 호출자와 참조 대상, 권한으로 걸러 낸다 |
| 도구 주석을 정책으로 다룬다 | 파괴적인 연산이 확인 절차를 건너뛴다 | 권한과 승인은 주석 바깥에서 강제한다 |
| 잘못된 도구 하나가 탐색을 무너뜨린다 | 서버 전체를 쓸 수 없게 된다 | 잘못된 기술자만 물리치고 유효한 도구는 따로 승인한다 |

## 캡스톤과의 연결 (Capstone Connection)

Phase 13의 캡스톤에는 서버 여러 대의 도구를 합칠 수 있는 게이트웨이가 필요하다. 이 레슨이 그 승인 핵심을 제공한다.

이 산출물로 캡스톤 근거 네 가지를 채점하라.

- 결과가 일정하고 빠짐없는 페이지 나누기 탐색.
- 모델에 노출하기 전의 기술자 검증.
- 검증된 구조화 출력과 한도가 걸린 콘텐츠 블록.
- 권한 경계를 지키는 완성 제안과 라우팅 메타데이터.

`tools/call` 한 번이 성공했다고 게이트웨이 호환성을 주장하지 마라. 기술자와 페이지 기록, 승인된 도구 집합, 물리친 도구 집합, 검증된 결과 하나를 함께 남겨라.

## 핵심 용어 (Key Terms)

| 용어 | 뜻 |
|------|---------|
| `inputSchema` | 도구가 받아들이는 인자를 정의하는 JSON Schema 객체 |
| `outputSchema` | `structuredContent`를 정의하는 선택적 JSON Schema |
| `structuredContent` | 도구 결과가 만들어 내는 임의의 JSON 값 |
| Content block | 타입이 붙은 텍스트, 이미지, 오디오, 자원 링크, 내장 자원 |
| `x-mcp-header` | 원시 타입 인자를 Streamable HTTP 메타데이터로 복사하게 하는 스키마 주석 |
| Opaque cursor | 서버가 발급하며 클라이언트가 값을 해석하지 않는 페이지 토큰 |
| Completion reference | 인자를 완성하려는 대상 프롬프트 이름이나 자원 URI 또는 템플릿 |
| Admission | 탐색된 기술자를 노출할지 물리칠지에 대한 클라이언트의 판단 |
