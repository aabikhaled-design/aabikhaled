# MCP 적합성 엔지니어링: 판본과 근거, 운영 (MCP Conformance Engineering: Versioning, Evidence, and Operations)

> SDK 하나로 정상 경로가 돌아갔다고 해서 그 서버가 적합한 것은 아니다. 적합성은 실제로 오가는 바이트에, 판본 경계에, 중간 장비를 지나는 길목에, 그리고 되돌리는 순간에 존재한다.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13 · 09 (transports), Phase 13 · 17 (gateways), Phase 13 · 30 (registry admission)
**Time:** ~100 minutes

## 학습 목표 (Learning Objectives)

- MCP의 규범 규칙을 정상 기록과 거부 기록으로 옮긴다.
- 엄격한 `2026-07-28` 동작과, 한도를 둔 구판 대체 동작을 따로 둔다.
- 덧붙은 모르는 필드와, 유효하지 않은 모르는 `resultType`을 구분한다.
- 날것의 JSON-RPC 근거와 SDK가 정규화한 뷰를 비교한다.
- 실제 프록시 경계를 지나서도 헤더와 본문의 무결성을 증명한다.
- 민감 정보를 가린 기록과 건강 상태, 되돌리기 근거로 배포를 통제한다.

## 문제 (The Problem)

SDK로 `tools/list`를 부르면 도구가 돌아온다. 통합 테스트가 통과한다.

그 결과는 중요한 질문에 답해 주지 않는다.

- 그 요청에 요청마다의 최신 프로토콜 메타데이터가 실려 있었는가?
- `MCP-Protocol-Version`과 `Mcp-Method`, `Mcp-Name`이 JSON-RPC 본문과 일치했는가?
- 응답에 유효한 `resultType`이 실제로 실려 있었는가, 아니면 SDK가 그것을 지어냈는가?
- 클라이언트가 앞으로 생길 덧붙은 필드를 보존하겠는가?
- 인식되는 최신 오류가 실수로 구판 초기화를 유발하지는 않는가?
- 프록시가 원본 서버의 상태와 JSON-RPC 오류를 그대로 보존했는가?
- 알림 직렬화기가 금지된 응답을 내보내지는 않았는가?
- 운영에서 비밀 값을 저장하지 않고도, 어떤 배포를 왜 올리고 왜 되돌렸는지 증명할 수 있는가?

적합성은 관측할 수 있는 불변 조건의 묶음이다. 실무 트래픽이 그것을 알려 주기 전에, 먼저 그 불변 조건을 붙잡는 하네스를 만들어라.

```figure
mcp-conformance-operations
```

## 판본 시대부터 나눠라 (Start With Version Eras)

MCP `2026-07-28`은 요청마다 스스로 담고 다니는 메타데이터를 쓴다. 최신 요청에는 `params._meta.io.modelcontextprotocol/protocolVersion`과 `params._meta.io.modelcontextprotocol/clientCapabilities`가 실린다. 이 이름 공간이 붙은 정확한 키가 중요하다. 이름 공간 없는 `protocolVersion`이나 `clientCapabilities` 별칭은 형식이 잘못된 것이다. HTTP 경계에 복사된 라우팅 헤더가 있다면, 그 값이 JSON-RPC 본문과 일치해야 한다. 최신 방식의 성공 결과에는 `resultType`이 실린다.

`2025-11-25`까지의 판본은 예전의 초기화 방식을 쓴다. `resultType`이 없는 구판 결과는, 클라이언트가 그 예전 방식을 고른 뒤에야 완료로 해석된다.

두 형식을 한꺼번에 받아들이는 느슨한 검증기 하나를 만들지 마라. 갈래를 둘로 두어라.

| 갈래 | 진입 근거 | `resultType`이 없을 때 | 초기화 |
|---|---|---|---|
| 최신 | 성공한 `server/discover`나 인식되는 최신 응답 | 유효하지 않다 | 기본 경로가 아니다 |
| 구판 | 설정된 허용 목록과, 결론이 나지 않은 최신 탐침 뒤의 유효한 구판 `initialize` 결과 | 완료로 해석한다 | 그 시대에서는 필수다 |

이렇게 나눠 두어야, 형식이 잘못된 최신 상대가 더 느슨한 검증이라는 보상을 받지 않는다.

### 엄격 모드

엄격 모드는 최신 방식으로 동작한다는 증거를 요구한다. 성공한 `server/discover`가 최신 갈래를 증명한다. 인식되는 최신 JSON-RPC 오류도 그것을 증명한다. 요청을 고치거나 멈춰라. 서버가 `-32020`이나 `-32021`, `-32022`를 돌려줬다는 이유로 절대 낮춰 잡지 마라.

### 대체 모드

대체 모드는 한도를 둔 최신 탐침을 한 번 던진다. 시간 초과나 빈 응답, 끊긴 연결, 인식되지 않는 응답은 결론이 나지 않은 것이다. 상대가 구판이라는 증명이 아니다. 호환성을 위해 명시적으로 설정되었거나 허용 목록에 든 엔드포인트만 그다음에 한도를 둔 구판 탐침을 받을 수 있고, 클라이언트는 그 탐침의 `initialize` 결과와 합의된 구판 개정판을 검증한 뒤에야 구판 갈래를 고른다.

대체는 "아무 오류나 나면 구판을 시도해 보기"가 아니다. 인식되는 최신 오류에는 고칠 방법에 대한 쓸모 있는 정보가 담겨 있다. 그것을 보고 낮춰 잡으면 헤더 불일치나 빠진 기능 선언, 지원하지 않는 판본이 가려진다.

이렇게 해야 공격자나 장애, 걸러 내는 프록시가 최신 응답을 떨어뜨려서 강제로 낮춰 잡게 만드는 일을 막을 수 있다. 엔드포인트 정책과, 결론이 나지 않은 최신 관측, 정확한 구판 증거, 고른 시대를 함께 기록하라.

기록마다 고른 시대를 나란히 남겨라. 그 사실이 없으면, 같은 빠진 필드가 어떤 실행에서는 괜찮아 보이고 다른 실행에서는 유효하지 않게 보인다.

## 기록 말뭉치를 만들어라 (Build a Transcript Corpus)

기록 고정 데이터는 SDK 호출만이 아니라 경계를 실제로 넘어간 것을 남긴다.

```json
{
  "name": "golden-modern-list",
  "era": "modern",
  "headers": {
    "MCP-Protocol-Version": "2026-07-28",
    "Mcp-Method": "tools/list"
  },
  "request": {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/list",
    "params": {
      "_meta": {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {}
      }
    }
  },
  "responseStatus": 200,
  "responseBody": {
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
      "resultType": "complete",
      "tools": []
    }
  }
}
```

고정 데이터는 두 갈래로 둔다.

### 정상 기록

정상 기록은 받아들여야 하는 동작을 증명한다.

- 메타데이터와 헤더가 일치하는 최신 탐색이나 메서드 요청.
- 필수 필드를 갖춘 완료 결과.
- 그 메서드가 추가 입력을 요청할 수 있을 때의 `input_required` 결과.
- 해당 기능을 미리 알린 뒤에만 나오는 확장 결과.
- `resultType`이 없는 구판 결과. 다만 구판 시대를 골랐을 때만 유효하다.
- JSON-RPC 응답 없이 처리되는 알림.

정상 기록은 크기보다 정확성이 중요하다. 자주 바뀌는 식별자와 시각은 결정적으로 고정하거나 비교 전에 정규화하라.

### 거부 기록

거부 기록은 물리쳐야 하는 동작을 증명한다.

- 헤더와 본문의 불일치.
- 요청마다 실어야 할 기능 정보 누락.
- 맞춰진 프로토콜 판본이 지원되지 않는 경우.
- 최신 방식인데 `resultType`이 없는 경우.
- 모르는 `resultType`이거나 알리지 않은 `resultType`.
- 응답의 `jsonrpc`가 `2.0`이 아니거나, 식별자의 값이나 JSON 타입이 다른 경우.
- 응답에 `result`와 `error`가 함께 있거나 둘 다 없는 경우.
- 정수 `code`와 문자열 `message`가 없는 오류.
- 알려진 프로토콜 오류를 엉뚱한 HTTP 상태에 대응시킨 경우.
- 알림에 응답을 내보낸 경우.
- 형식이 잘못된 JSON-RPC 봉투.
- 프록시가 프로토콜 오류를 뭉개 버린 경우.

거부 사례마다 물리치는 경계와 안정된 오류 코드를 단언하라. "호출이 실패했다"로는 부족하다. 프록시가 만든 500과 원본 서버의 `-32020`은 둘 다 실패처럼 보이지만 운영자에게 전혀 다른 이야기를 들려준다.

헤더 불일치 고정 데이터에는 요청 식별자가 맞고 오류 코드가 `-32020`인, 서버의 실제 HTTP 400 JSON-RPC 응답이 들어 있어야 한다. 로컬 검증기가 `HeaderMismatch`를 관측할 때마다 이것을 자동으로 강제하라. 응답 확인을 고정 데이터의 선택 플래그로 두지 마라. HTTP 500에 본문이 없는 사례는, 로컬에서 물리친 코드가 맞았더라도 실패다. 자기 요청 검증기가 예외를 던지는 데서 멈추는 하네스는 자기 자신만 시험한 것이지 서버의 실제 동작을 시험한 것이 아니다.

공식 MCP 적합성 프로젝트는 외부 시험 묶음이자 판본이 관리되는 기준으로 쓸모가 있다. 그래도 로컬 기록을 함께 두어라. 그 기록은 우리 프록시와 SDK, 인증, 확장, 배포 경로를 담고 있고, 일반 시험 묶음은 그것을 알 수 없다.

## 헤더 값은 RPC 본문과 일치해야 한다 (Header Values Must Match the RPC Body)

최신 Streamable HTTP에서 중간 장비는 복사된 헤더로 경로를 정하거나 정책을 강제할 수 있다. 그래도 프로토콜의 정본은 JSON-RPC 본문이다. 둘이 어긋나면 그것은 무결성 실패이지, 둘 중 하나를 고르라는 힌트가 아니다.

다음 순서로 검증하라.

1. JSON-RPC 봉투와 메타데이터 타입을 파싱하고 검증한다.
2. `MCP-Protocol-Version`과 `params._meta.io.modelcontextprotocol/protocolVersion`을 비교한다.
3. `Mcp-Method`와 `method`를 비교한다.
4. 그 메서드에 라우팅 이름이 있다면 `Mcp-Name`을 본문의 대응 값과 비교한다.
5. 서로 같다는 것이 확인된 뒤에, 맞춰진 판본과 기능 집합을 지원하는지 판단한다.

이 순서가 불일치 `-32020`과 지원하지 않는 판본 `-32022`를 갈라 준다. 그리고 게이트웨이는 헤더의 이름으로 권한을 주고 원본 서버는 본문의 다른 이름을 실행하는 일도 막아 준다.

HTTP 필드 이름은 대소문자를 가리지 않지만 그 값은 대소문자를 가린다. 찾기 전에 헤더 이름을 정규화하고, 서로 충돌하는 중복은 물리쳐라. `Mcp-Name`이 안전하지 않은 문자나 비ASCII를 담고 있거나 앞뒤에 공백이 있다면, 본문과 비교하기 전에 정확한 `=?base64?{Base64EncodedValue}?=` UTF-8 표식을 해독하라. 표식이 잘렸거나 Base64가 잘못되었거나 UTF-8이 잘못되었거나 안전하지 않은 날것의 값이라면 `-32020`으로 물리쳐라. 앞뒤 공백이 날것으로 온 경우는 본문에 같은 글자가 있더라도 유효하지 않다. 그 값은 전송 전에 표식 인코딩을 거쳤어야 하기 때문이다.

중간 장비는 형식이 잘못된 HTTP를 MCP 서버에 닿기 전에 물리칠 수 있다. 그래서 그 실패는 JSON-RPC 없는 HTTP 오류일 수 있다. 그 거부가 중간 장비에서 왔는지 원본 서버에서 왔는지 기록하라. 원본 MCP 서버가 유효한 JSON-RPC 요청을 처리했다면 프로토콜 오류 계약을 써야 한다.

## 모르는 필드와 모르는 결과 유형은 다르다 (Unknown Fields Are Not Unknown Results)

앞으로의 호환성을 위해서는 서로 다른 규칙이 둘 필요하다.

### 덧붙은 모르는 필드

결과 객체와 `_meta` 맵에는 필드가 늘어날 수 있다. 검증기는 그 필드가 예약된 계약을 어기지 않는 한, 자기 역할에 맞게 그것을 보존하거나 무시해야 한다. 예제는 날것의 결과 전체를 근거로 남기고, 알려진 결과 옆의 `futureHint`를 받아들인다.

투명한 프록시라면 모르는 필드를 그대로 두는 편이 대체로 안전하다. 애플리케이션 클라이언트라면 무시해도 유효할 수 있다. 그래도 차이 비교 테스트는 SDK가 그것을 빠뜨렸다는 사실을 드러내서, 그 동작이 의도한 것이 되게 해야 한다.

### 모르는 `resultType`

`resultType`은 갈래를 가르는 값이다. 최신 방식의 핵심 결과는 `complete`나 `input_required`를 쓴다. 확장은 자기 기능을 미리 알린 뒤에만 다른 값을 더할 수 있다. 예를 들어 Tasks 확장은 그렇게 합의된 맥락에서 `task`를 더할 수 있다.

모르거나 알리지 않은 갈래 값을 완료로 다루면 안전하지 않다. 클라이언트는 자기가 버리게 될 수명 주기가 무엇인지 모른다. 그것을 물리쳐라.

그래서 같은 날것의 응답 안에, 받아들여도 되는 모르는 필드와 받아들이면 안 되는 모르는 결과 유형이 함께 있을 수 있다. 두 경우를 모두 시험하라.

갈래 값은 첫 겹일 뿐이다. 그다음에 메서드별 본문을 검증하라. 완료된 `tools/list` 결과에는 `tools` 배열이 있어야 하고, 그 기술자들은 비어 있지 않고 서로 다른 이름과 쓸모 있는 설명, 객체를 최상위로 하는 `inputSchema`를 가져야 한다. `task` 결과는 Tasks 기능을 갖춘, 자격 있는 `tools/call`에서만 유효하며 `taskId`와 알려진 상태, 생성 및 갱신 시각, `ttlMs`, 그리고 선택적인 유효한 조회 간격을 요구한다. 완료된 `completion/complete` 결과에는 문자열 값이 100개를 넘지 않는 `completion` 객체와, 돌려준 값의 개수보다 작지 않은 선택적 음이 아닌 정수 `total`, 선택적 참·거짓 값 `hasMore`가 필요하다. `resultType`의 철자가 맞다고 해서 형식이 잘못된 본문이 적합해지지는 않는다.

## 알림의 불변 조건 (The Notification Invariant)

JSON-RPC 알림에는 `id`가 없다. 받는 쪽은 JSON-RPC 성공 응답도 오류 응답도 보내서는 안 된다.

HTTP 알림 형태를 받아들일 때, 하네스는 본문이 빈 HTTP `202`를 기대한다. MCP `2026-07-28`은 Streamable HTTP에서 클라이언트가 서버로 보내는 핵심 알림을 정의하지 않는다. 예제는 일방향 직렬화 불변 조건을 시험하려고, 이름 공간이 붙은 이 커리큘럼용 확장 알림만 쓴다. 그것을 새로운 핵심 메서드처럼 소개하지 마라.

핸들러만이 아니라 직렬화기를 시험하라. 핸들러는 `None`을 돌려주는데 미들웨어가 그것을 JSON 성공 객체로 감쌀 수 있다. 최종적으로 나가는 바이트를 붙잡아라.

## SDK 차이 비교를 더하라 (Add an SDK Differential)

SDK는 통신 객체를 언어에 맞는 편한 타입으로 바꾸는 경우가 많다. 쓸모 있는 일이지만, 정규화된 객체로는 무엇을 받았는지 증명할 수 없다.

위험이 큰 고정 데이터마다 다음을 붙잡아라.

1. SDK가 해독하기 전의 날것 상태와 헤더, 응답 본문.
2. SDK가 돌려준 정규화된 값이나 예외.
3. 고른 시대에서 기대하는 의미상의 결과.
4. SDK가 끌어올렸거나 지어냈거나 떼어 냈거나 바꾼 필드.

예제는 `resultType`과 `_meta`, `ttlMs`, `cacheScope` 같은 알려진 통신 관리용 필드를 SDK가 없애는 것은 허용하면서 애플리케이션 본문을 비교한다. 그리고 `futureHint`가 사라진 것은 의미를 담은 모르는 필드가 없어진 것이므로 보고한다.

모든 차이를 SDK의 결함으로 여기지 마라. 요점은 그 변환을 눈에 보이게 만드는 것이다. 우리 구성 요소가 덧붙은 필드를 무시해도 되는 애플리케이션 엔드포인트인지, 아니면 그것을 보존해야 하는 투명한 중간 장비인지 정하라.

배포하는 SDK와 판본마다 이 차이 비교를 돌려라. 같은 기록을 두 SDK가 다르게 정규화한다면, 결과를 보고 편한 쪽을 고르는 대신 배포 정책이 어느 동작을 받아들일지 정해야 한다.

## 프록시 근거를 붙잡아라 (Capture Proxy Evidence)

실무의 MCP 실패는 대개 여러 프로세스에 걸쳐 일어난다. 세 가지 시점을 기록하라.

| 시점 | 최소한의 근거 |
|---|---|
| 유입 | 요청 헤더, JSON-RPC 본문, 콘텐츠 타입, 인증된 경로, 받은 시각 |
| 원본 | 전달된 헤더와 본문 해시, 원본 상태, 응답 헤더와 본문 |
| 유출 | 클라이언트에게 보이는 상태와 헤더, 본문, 보낸 시각 |

예제는 흔한 변형 두 가지를 잡아낸다.

- 원본의 HTTP 400이나 404 JSON-RPC 오류가 프록시의 일반적인 500으로 바뀌는 경우.
- 나가는 JSON-RPC 본문이 원본 본문과 다른 경우.

콘텐츠 타입과 `Accept`, 압축, 요청 단위 SSE, 캐시 헤더, 추적 상관 관계에 대해 배포 환경에 맞는 단언을 더하라. 정책이 허용한다면 TLS 종료의 양쪽을 모두 붙잡아라. 경로를 증명하겠다고 자격 증명을 기록하지는 마라.

## 근거가 메모리를 떠나기 전에 가려라 (Redact Before Evidence Leaves Memory)

가리기는 나중에 하는 정리 작업이 아니라 적합성 운영의 일부다. 직렬화나 해싱, 로그, 테스트 산출물, 실패 보고 업로드보다 먼저 적용하라.

예제는 키 이름의 대소문자를 맞추고 구분자를 없앤 뒤에 대조하고, `Authorization`과 `Cookie`, `Set-Cookie`, `X-Api-Key`, `accessToken`, `clientSecret`, `registrationAccessToken`, `token`, `password`, `secret`, `api_key` 같은 키 아래의 값을 재귀적으로 바꾼다. 정규화와 금지 목록이 같은 형태를 써야, 카멜 표기와 하이픈, 밑줄, 점 표기 변형이 서로의 정책을 빠져나가지 못한다. 실무 수집기라면 메서드별 인자 정책을 더해야 한다. `query`처럼 무해해 보이는 키에도 개인정보나 규제 대상 데이터가 들어 있을 수 있기 때문이다.

가린 근거 묶음을 해시하라. 날것의 기록은 특정 조사가 필요할 때만, 승인된 단기 보관 시스템에 두라. 해시는 어떤 가린 묶음이 그 판단을 이끌었는지를 증명할 뿐, 지운 값을 드러내지는 않는다.

## 건강 상태와 되돌리기를 관문에 넣어라 (Make Health and Rollback Part of the Gate)

프로토콜 적합성은 배포에 반드시 필요하지만 그것만으로는 부족하다. 적합한 후보도 시간 초과를 내거나 메모리를 흘리거나 의존 서비스를 과부하시킬 수 있다.

배포 전에 건강 관측 구간을 정의하라.

- 최소 표본 수.
- 최대 오류율.
- 최대 지연 시간 백분위.
- 포화도나 자원 한도.
- 관측 기간.
- 승인된 기준선과의 비교.

배포 전에 되돌리기 근거도 정의하라.

- 정확한 이전 판본.
- 승인 근거 해시.
- 산출물과 기술자의 SHA-256 고정 값.
- 지금의 레지스트리 상태.
- 지금의 건강 검사 결과.
- 경로 복원 절차.
- 믿을 수 있는 배포 통제기 신원이 그 정확한 필드들에 대해 만든 증명.

후보가 실패한 뒤가 아니라, 올리기 전에 그 되돌리기 대상이 검증되고 건강한지 확인하라. 쓸 만한 복구 경로 없이 성공한 배포는 실무에 쓸 준비가 된 것이 아니다.

후보가 실패했는데 되돌릴 대상에 그런 근거가 없다면, 짐작하지 말고 트래픽을 멈춰라. "있던 걸로 되돌려"는 운영 통제가 아니다.

준비 여부를 참·거짓 검사로 줄이지 마라. 판본 문자열이 비어 있지 않다거나 `healthy: "yes"`라거나 임의의 근거 문자열이 있다는 식으로는 안 된다. 예제는 정확한 타입과 활성 상태, SHA-256 해시 세 개, 믿을 수 있는 서명자, 그리고 되돌리기 정보 전체에 대한 유효한 HMAC-SHA-256 증명을 요구한다. 데모의 결정적인 키는 비밀이 아닌 고정 데이터다. 실무에서는 보호된 키나 KMS 검증 결과, 공개 키 증명 검증기를 배포 경계에서 주입하라.

배포 관문은 기록이나 SDK 차이, 프록시 근거가 비어 있으면 물리친다. 각 근거에는 유효한 해시가 있어야 한다. 건강 관측 구간이 초록색이라고 해서, 한 번도 관측하지 않은 경계를 채워 주지는 못한다.

## 직접 만들기 (Build It)

표준 라이브러리만 쓰는 하네스를 실행한다.

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
```

데모는 유효한 완성 결과와 형식이 잘못된 완성 결과를 포함해 정상 기록과 거부 기록 열다섯 개를 정확히 돌리고, 날것의 결과와 SDK 뷰를 비교하고, 원본 오류를 뭉갠 프록시를 살펴보고, 건강 상태를 평가하고, 되돌리기 근거를 인증하고, 그 대상을 고른다.

예상되는 모양은 이렇다.

```json
{
  "transcriptsPassed": 15,
  "transcriptsTotal": 15,
  "sdkDroppedFields": ["futureHint"],
  "proxyIssues": [
    "proxy collapsed a protocol error into HTTP 500",
    "proxy changed the origin JSON-RPC body"
  ],
  "releaseAction": "rollback",
  "evidenceDigest": "..."
}
```

`code/main.py`를 다음 순서로 읽어라.

1. `validate_request()`가 시대별 요청 규칙과 헤더 규칙을 강제한다.
2. `validate_result()`가 구판의 빠진 갈래 값과 유효한 최신 값, 확장, 모르는 값을 가른다.
3. `select_era()`가 엄격 정책과 한도를 둔 대체 정책을 구현한다.
4. `run_transcript()`가 정상 고정 데이터와 거부 고정 데이터를 평가한다.
5. `compare_sdk_view()`가 정규화로 생긴 차이를 드러낸다.
6. `inspect_proxy()`가 유입과 원본, 유출 근거를 비교한다.
7. `redact()`가 근거를 해싱하기 전에 뻔한 비밀 값을 없앤다.
8. `rollback_evidence_ready()`가 정확한 고정 필드와 믿을 수 있는 배포 증명을 검증한다.
9. `ReleaseGate.evaluate()`가 비어 있지 않은 적합성과 SDK, 프록시, 건강, 되돌리기 근거를 맞물린다.

## 실제로 써 보기 (Use It)

이 하네스를 네 지점에서 돌려라.

1. 구현을 바꿀 때마다, 프로세스 안의 테스트 어댑터로.
2. 빌드된 클라이언트와 서버 바이너리를 실제 전송 계층으로 이어서.
3. 스테이징 환경에서 배포된 프록시나 게이트웨이를 거쳐서.
4. 카나리 배포 중에 실제 건강 상태와 되돌리기 근거를 붙여서.

계층이 달라져도 사례 이름은 그대로 유지하라. `negative-header-body-mismatch`는 단위 시험과 전 구간 시험, 프록시 시험, 카나리 보고서에서 같은 불변 조건을 뜻해야 한다. 경계가 달라졌으니 근거 해시는 달라지겠지만, 요구 사항은 달라져서는 안 된다.

고정 데이터의 스키마는 버전 관리에 두라. 가린 실행 근거는 배포 시스템에 두라. 날것의 기록은 사고 대응 접근 통제 아래에 잠깐만 두라.

### 실습 A: 시대 경계를 증명하기

`code` 디렉터리에서 Python을 연다.

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations/code

```

이렇게 실행한다.

```python
from main import *
validate_result({"tools": []}, "legacy")
validate_result({"tools": []}, "modern")
```

구판 호출은 `complete`로 해석한다. 최신 호출은 `ProtocolViolation`을 일으킨다. 이제 대체 동작을 시험한다.

```python
select_era({"kind": "timeout"}, "fallback")
select_era(
    {"kind": "timeout"},
    "fallback",
    legacy_allowed=True,
    legacy_evidence={"kind": "initialize_success", "protocolVersion": LEGACY_VERSION},
)
select_era({"kind": "jsonrpc_error", "code": -32021}, "fallback")
```

첫 번째 시간 초과는 물리쳐진다. 조용하다는 것이 구판이라는 근거가 아니기 때문이다. 두 번째 호출은 설정이 허용했고 유효한 구판 초기화 결과를 관측했기 때문에만 구판을 고른다. 인식되는 기능 누락 오류는 최신 갈래를 증명한다.

### 실습 B: 덧붙은 필드와 갈래 값

```python
validate_result({"resultType": "complete", "tools": [], "futureHint": True}, "modern")
validate_result({"resultType": "future_mode", "tools": []}, "modern")
```

첫 번째 결과는 `futureHint`를 보존한다. 두 번째는 수명 주기 갈래 값이 모르는 것이라 물리쳐진다.

### 실습 C: SDK 변환 살펴보기

```python
compare_sdk_view(
    {"resultType": "complete", "tools": [], "futureHint": {"mode": "new"}},
    {"tools": []},
)
```

우리 구성 요소가 `futureHint`를 무시해도 되는지, 아니면 그대로 넘겨야 하는지 정하라. 그 선택을 배포 정책에 적어 두라. 차이 비교 결과를 조용히 지우지 마라.

### 실습 D: 프록시 고치기

데모의 교환을 고쳐서 유출 지점이 원본의 상태와 본문을 그대로 보존하게 하라. `python3 main.py`를 다시 돌려라. 프록시 문제는 사라지지만 SDK 차이가 여전히 올리기를 막는다. 그다음 SDK 뷰에 `futureHint`를 포함시키고, 모든 근거가 통과할 때 조치가 `promote`로 바뀌는 것을 확인하라.

## 연습 실습 (Practice Lab)

요청 단위 SSE 기록을 하네스에 추가하라.

요구 사항은 이렇다.

- 응답 상태와 콘텐츠 타입, 순서가 있는 SSE 이벤트, 스트림 종료를 붙잡는다.

- 헤더와 본문이 어긋나면 최신 방식의 불일치 코드를 돌려준다.
- 응답 판본과 식별자, `result`와 `error`의 배타성, 오류 형태, HTTP 대응이 검증된다.
- 메서드별 도구 목록과 태스크, 완성 결과 본문의 요구 사항이 강제된다.
- 관측된 `HeaderMismatch`마다 실제 HTTP 400 JSON-RPC `-32020` 응답을 요구한다.
- 날것의 `Mcp-Name` 공백은 물리치고, 정확한 표식 인코딩을 거친 공백은 그대로 되돌아온다.
- `resultType`이 없는 것은 구판 시대를 골랐을 때만 유효하다.
- 덧붙은 필드는 날것 검증에서 살아남고 모르는 결과 유형은 실패한다.
- 확장 결과 유형은 그 기능을 미리 알린 경우에만 통과한다.
- 인식되는 최신 오류가 구판 대체를 일으키지 않는다.
- 알림은 JSON-RPC 응답을 내지 않는다.
- SDK가 통신 관리용 필드를 없앤 것과 의미를 담은 필드를 잃은 것을 구분한다.
- 프록시의 오류 뭉개기를 잡아내고, 카멜 표기와 구분자 변형을 가로질러 자격 증명을 재귀적으로 가린다.
- 올리기는 비어 있지 않은 기록과 SDK, 프록시 근거, 그리고 건강한 운영 근거를 요구한다.
- 올리기와 되돌리기 모두, 인증되고 고정되고 활성이며 건강한 되돌리기 대상을 요구한다.

## 실무에서 겪는 실패 양상 (Production Failure Modes)

| 실패 | 허술한 테스트가 보고하는 것 | 하네스가 증명해야 하는 것 |
|---|---|---|
| SDK가 빠진 갈래 값을 지어낸다 | "tools/list 통과" | 날것의 최신 결과에 `resultType`이 없었고 유효하지 않다 |
| 클라이언트가 `-32021` 뒤에 낮춰 잡는다 | "구판 재시도가 되었다" | 인식되는 최신 오류는 대체를 금지한다 |
| 모르는 결과 유형을 완료로 다룬다 | "응답이 파싱되었다" | 알리지 않은 수명 주기 갈래 값은 물리친다 |
| 프록시는 한 도구를 허가하고 원본은 다른 도구를 실행한다 | "요청이 서버에 닿았다" | 모든 구간에서 `Mcp-Name`이 본문의 라우팅 이름과 같다 |
| 하네스가 서버 응답을 읽기 전에 예외를 던진다 | "헤더 불일치 테스트 통과" | HTTP 400과 JSON-RPC `-32020` 응답을 붙잡아 검증한다 |
| 프록시가 원본 400을 일반적인 500으로 바꾼다 | "상위 오류" | 원본과 유출 지점의 상태와 JSON-RPC 본문이 보존된다 |
| 알림 미들웨어가 `{result: null}`을 내보낸다 | "핸들러가 None을 돌려줬다" | 최종적으로 나가는 본문이 비어 있고 JSON-RPC 응답이 없다 |
| SDK가 덧붙은 필드를 떼어 낸다 | "타입 객체가 일치한다" | 날것 뷰와 정규화 뷰가 정확히 어떤 필드가 사라졌는지 보여 준다 |
| 실패 기록에 접근 토큰이 샌다 | "디버그 묶음을 올렸다" | 해싱과 로그, 업로드보다 먼저 가리기가 일어났다 |
| 자격 증명 키의 표기 방식이 가리기를 빠져나간다 | "금지 목록에 api_key가 있다" | 카멜 표기와 구분자 변형이 하나의 정규화된 금지 형태를 공유한다 |
| 카나리에 표본이 없는데 건강해 보인다 | "오류 0건" | 최소 표본 수를 강제한다 |
| 되돌리기가 모르는 빌드를 고른다 | "이전 배포를 복원했다" | 대상 판본과 승인 해시, 고정 값, 상태, 건강 상태가 모두 있다 |

## 운영 원칙 (Operational Rule)

우리가 보내는 바이트와, 중간 장비가 전달하는 바이트와, SDK가 드러내는 의미와, 압박 속에서 운영이 실제로 쓸 근거를 시험하라. 호환성은 명시적인 갈래다. 되돌리기는 근거로 뒷받침되는 배포 조치다. 어느 쪽도 느슨한 파서가 만들어 낸 우연한 부수 효과여서는 안 된다.
