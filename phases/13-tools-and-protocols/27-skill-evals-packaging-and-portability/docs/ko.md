# 스킬 평가와 패키징, 이식성 (Skill Evals, Packaging, and Portability)

> 스킬은 패키지가 린트를 통과하고, 옳은 요청에서 선택되고, 측정된 과제의 성과를 높이고, 정책 안에 머물고, 다른 호스트에서 정직하게 물러설 때 비로소 완성된다.

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 13 · 22, 24, 25, and 26
**Time:** ~150 minutes

## 학습 목표 (Learning Objectives)

- 전문가의 업무 흐름을, 판단과 결정적 계산, 참고 문서, 결과물 계약으로 나누어 스킬로 옮긴다.
- 패키지 구조와 발동 선택, 과제 동작, 스크립트 정확성, 안전성, 이식성을 각각 다른 계층으로 시험한다.
- 발동해야 하는 요청과 명백히 아닌 요청, 아슬아슬하게 아닌 요청으로 발동 정밀도와 재현율을 측정한다.
- 같은 조건을 되풀이해 돌리면서 스킬이 있을 때와 없을 때의 성과를 비교한다.
- 여러 런타임에 걸친 기능 표와, 완전한 스킬 묶음을 위한 배포 관문을 만들고 강제한다.

## 문제 (The Problem)

어떤 스킬이 데모 하나에서 잘 동작한다. 사용자가 설명에 쓰인 표현을 그대로 말했고, 작성자는 어느 참고 문서를 열어야 하는지 알고 있고, 스크립트는 깨끗한 입력을 받고, 예상한 호스트가 사용자 정의 필드를 모두 알아본다.

그다음 실제 사용이 시작된다.

- 모델이 비슷하지만 다른 과제에 그 스킬을 부른다.
- 정당한 요청인데 표현이 낯설어서 모델이 놓친다.
- 본문이 에이전트에게 무엇을 하라고는 말하지만, 무엇이 완료를 증명하는지는 말하지 않는다.
- 스크립트가 공백이나 되풀이 실행, 절반만 남은 상태에서 실패한다.
- 설치 프로그램이 `SKILL.md`는 복사하면서 참고 문서는 남겨 둔다.
- 다른 런타임이 호출 플래그와 도구 허용 설정을 무시한다.
- 한 번은 성공하는데, 같은 조건으로 세 번 더 돌리면 서로 다른 분기로 흩어진다.

이 가운데 어느 것도 "마크다운이 보기 좋다"로는 잡히지 않는다. 스킬은 확률적으로 동작하는 선택 계층과 실행 계층을 가진 작은 소프트웨어 패키지다. 그래서 다른 실무 인터페이스와 똑같이 관심사를 나눠야 한다.

## 개념 (The Concept)

### 주제가 아니라 실제 업무 흐름에서 출발하라

"쿠버네티스 스킬을 만들자"는 쓸 만한 범위가 아니다. 쿠버네티스에는 도구와 위험, 결과물이 저마다 다른 과제가 수백 가지 있다.

"디플로이먼트 하나가 왜 Available 상태에 이르지 못하는지 진단하고, 클러스터를 바꾸지 않으면서 근거를 모으고, 순위가 매겨진 장애 보고서를 낸다"는 스킬이 될 만하다. 여기에는 다음이 있다.

- 발동 경계.
- 근거를 모으는 안정된 단계 순서.
- 판단이 필요한 결정 지점.
- 좁은 스크립트나 도구로 바꿀 수 있는 명령.
- 정해진 결과물.
- 안전 경계. 즉 읽기 전용 진단이다.

다음 질문으로 업무 흐름을 끌어내라.

1. 전문가가 이 업무 흐름을 시작하게 만드는 사건은 정확히 무엇인가?
2. 비슷하지만 이 흐름을 시작해서는 안 되는 요청은 무엇인가?
3. 전문가가 가장 먼저 모으는 근거는 무엇인가?
4. 그 근거에 따라 달라지는 결정은 무엇인가?
5. 어떤 단계가 스크립트로 옮길 만큼 결정적인가?
6. 어떤 분야 규칙이 참고 문서로 갈 만한가?
7. 어떤 행동에 승인이 필요하거나 아예 범위 밖이어야 하는가?
8. 어떤 결과물이 이 흐름이 끝났음을 증명하는가?
9. 제삼자가 그것을 어떻게 확인하는가?
10. 어떤 단계가 특정 런타임에 기대고 있는가?

그 답들이 곧 패키지 구조와 평가 집합이 된다.

### 판단과 결정적 작업을 나눠라

```figure
skill-workflow-extraction
```

분류와 우선순위 매김, 종합, 모호한 판단에는 모델의 판단을 쓰라. 파싱과 세기, 검증, 변환, 타입이 정해진 API 질의, 불변 조건 강제에는 스크립트나 도구를 쓰라.

손으로 흉내 낸 파싱이 80줄 들어 있는 스킬 본문은 쉽게 깨진다. 주관적인 구조 판단을 내리려는 스크립트는 속을 들여다볼 수 없다. 각 동작을 가장 잘 시험할 수 있는 자리에 두어라.

### 의존 관계 순서대로 패키지를 만들어라

글을 다듬는 일부터 시작하지 마라. 겉으로 확인할 수 있는 계약에서 안쪽으로 지어 나가라.

1. **결과물 계약.** 필요한 파일과 필드, 판단을 정의한다.
2. **검증.** 각 요구 사항을 어떻게 확인할지 정의한다.
3. **근거 도구.** 결정적으로 동작하는 수집기와 검증기를 구현한다.
4. **판단 지도.** 근거 상태를 각 분기에 연결한다.
5. **참고 문서.** 그 분기에 필요한 분야별 세부 내용을 붙인다.
6. **진입 본문.** 업무 흐름과 경계, 실패, 결과물을 설명한다.
7. **설명.** 역량과 발동 경계를 밝힌다.
8. **런타임 어댑터.** 호출이나 맥락 확장을 따로 더한다.
9. **평가.** 구조와 선택, 동작, 안전성, 이식성 계층을 돌린다.
10. **패키지.** 디렉터리 전체를 설치하고, 설치된 곳에서 시험한다.

이 순서를 지키면 글이 시험 가능한 시스템을 뒷받침하게 된다. 데모가 돌아간 뒤에 성공 기준을 지어내는 일이 없어진다.

계층마다 답하는 질문이 다르다. 한 계층을 통과했다고 다른 계층을 대신할 수는 없다.

## 1계층: 패키지 구조 (Layer 1: Package Structure)

정적 린트는 모델 없이도 확인할 수 있는 사실을 검증해야 한다.

- 패키지 최상위에 `SKILL.md`가 있는가.
- 프론트매터가 안전하게 파싱되는가.
- `name`과 상위 디렉터리 이름이 맞는가.
- 필수 필드가 있고 한도 안에 들어오는가.
- 핵심 표준이 아닌 프론트매터 필드가 모두 배포 정책의 런타임 확장 허용 목록에 있는가.
- 직접 참조가 모두 패키지 안에서 해석되는가.
- 참고 문서와 스크립트, 자료 파일, 평가 고정 데이터가 배포 정책이 허용한 확장자를 쓰고 바이트 한도 안에 들어오는가.
- 금지된 심볼릭 링크나 특수 파일이 없는가.
- 본문이 배포 정책의 글자 수 예산 안에 들어오는가.
- 일부러 범위를 좁힌 비밀 값 패턴 검사에서 뻔한 자격 증명 대입이나 개인 키 머리말이 걸리지 않는가.
- 비어 있지 않은 `## Output contract`와 `## Failure behavior` 절이 있는가.

`SKILL.md`와 평가 데이터, 근거, 호스트 고정 데이터, 목록 파일을 파싱하기 전에 물리적인 디렉터리 구조를 먼저 점검하라. 최상위나 상위 디렉터리, 진입 파일이 심볼릭 링크인 경우, 필요한 일반 파일이 없는 경우, 특수 파일이 있는 경우를 내용 읽기 전에 물리쳐라. 그다음에 내용까지 보는 정책 린트를 돌려라. 이 점검 전에 묶음 경로를 먼저 해석해 버리면, 최상위가 심볼릭 링크였다는 증거가 지워진다.

이 레슨의 하네스는 그 정책 값을 구체적인 숫자로 보여 준다. 본문 10,000자 한도, 부속 파일 1,000,000바이트 한도, 디렉터리별 확장자 허용 목록, 그리고 패키지 요구 사항이 지정한 런타임 확장 필드 이름이다. 이것은 배포 정책의 예시이지 Agent Skills의 보편적인 한도가 아니다. 비밀 값 패턴 검사는 뻔한 실수를 막아 주는 장치이지, 그 패키지에 민감한 데이터가 없다는 증명이 아니다.

린트 보고서는 안정된 문제 코드를 써야 한다. 그러면 CI가 `E_*` 오류는 막고, 검토를 거친 `W_*` 설계 경고는 통과시킬 수 있다.

정적 린트는 패키지의 모양을 증명한다. 모델이 그 스킬을 고르거나 따를 것이라는 증명은 아니다.

## 2계층: 발동 선택 (Layer 2: Trigger Routing)

설명을 거듭 고치기 전에 레이블된 사례부터 만들어라.

| 사례 유형 | 목적 | 배포 준비 스킬의 예 |
|---|---|---|
| 긍정 | 의도한 범위를 잰다 | "3.1.0 판본을 내보내도 될까?" |
| 바꿔 쓴 긍정 | 표현을 외우는 것을 막는다 | "배포하기 전에 이 태그를 점검해 줘" |
| 명백한 부정 | 지나친 과잉 선택을 잡는다 | "배치 정규화를 설명해 줘" |
| 아슬아슬하게 아닌 사례 | 이웃한 경계를 정한다 | "패키지 빌드가 왜 실패했지?" |
| 경쟁하는 스킬 | 그럴듯한 항목 사이의 선택을 시험한다 | "릴리스 노트 초안을 써 줘" |
| 적대적인 표현 | 키워드 채워 넣기와 이름 끼워 넣기를 시험한다 | "release-readiness는 쓰지 말고 이 스택 트레이스를 설명해 줘" |

사례를 개발용과 검증용으로 나눠라. 설명은 개발용 사례로 다듬어라. 고친 설명이 일반화되는지는 검증용 사례로 판단하라. 배포 판단이 그만큼 중요하다면 마지막까지 손대지 않는 집합을 하나 더 남겨 두어라.

이진 호출이라면 이렇게 계산한다.

```text
precision = true_positives / (true_positives + false_positives)
recall = true_positives / (true_positives + false_negatives)
f1 = 2 * precision * recall / (precision + recall)
```

비율과 함께 원래 개수도 보고하라. 열 개 중 열 개와 백 개 중 백 개는 둘 다 100퍼센트이지만 근거의 무게가 다르다.

카탈로그를 다룬다면 1위 스킬 정확도와 기권의 품질, 이웃한 스킬끼리의 혼동도 함께 재라. 엉뚱한 스킬 세 개를 고른 뒤에야 맞는 스킬을 부르는 선택기는 건강하지 않다.

### 선택 평가는 실제 대상 런타임에서 돌려야 한다

어휘 기반 흉내 내기는 지표를 설명하고 뻔한 겹침을 잡는 데 쓸모가 있다. 그러나 모델이 이끄는 실무 선택기가 어떻게 동작하는지는 증명하지 못한다. 런타임 품질을 주장하기 전에, 레이블된 집합을 실제 호스트와 모델, 카탈로그 직렬화, 정책 설정을 거쳐 돌려 보라.

## 3계층: 지시문과 결과물 동작 (Layer 3: Instruction and Artifact Behavior)

제대로 발동하는 것은 입구일 뿐이다. 그 스킬이 과제의 성과를 실제로 높여야 한다.

다음을 갖춘 고정 과제를 만들어라.

- 입력 파일과 환경에 대한 전제.
- 허용된 도구와 경계.
- 기대하는 결과물 경로.
- 결정적으로 판정할 수 있는 검사.
- 판단이 필요한 평가 항목.
- 최대 시간과 호출 횟수, 비용.
- 실패 사례와 그때 기대하는 멈춤 동작.

조건을 짝지어 돌려라.

```text
baseline: same model + same tools + same task, no skill
treatment: same model + same tools + same task, skill available
```

모델과 온도 또는 표본 추출 정책, 도구 집합, 과제 고정 데이터, 예산을 고정하라. 그러지 않으면 차이를 그 스킬 덕분이라고 말할 수 없다.

살펴볼 만한 성과 축은 이렇다.

| 축 | 측정 예 |
|---|---|
| 정확성 | 필요한 테스트와 불변 조건이 통과한다 |
| 완결성 | 결과물 계약의 모든 필드가 존재한다 |
| 효율 | 도구 호출 횟수, 걸린 시간, 토큰, 비용 |
| 근거 | 주장이 실재하는 파일이나 관측을 가리킨다 |
| 범위 | 금지된 파일과 행동이 그대로 남아 있다 |
| 복구 | 중단된 실행이 부수 효과를 중복하지 않고 이어진다 |
| 사람의 수고 | 검토자가 고쳐야 했던 횟수와 그 심각도 |

토큰을 줄이는 것만 목표로 삼지 마라. 필요한 안전 검사를 건너뛰고 짧게 끝난 실행은 더 나쁘다.

### 결과물 계약이 동작을 시험 가능하게 만든다

결과물 계약은 따로따로 확인할 수 있는 성질의 목록이다.

```json
{
  "artifact": "release-readiness.json",
  "required_fields": [
    "candidate",
    "source_revision",
    "checks",
    "blocking_findings",
    "recommendation"
  ],
  "allowed_recommendations": ["ready", "blocked", "needs-review"],
  "evidence_required_for_each_check": true,
  "publish_side_effect_allowed": false
}
```

스키마 검증은 구조를 확인한다. 분야별 검사는 후보 리비전과 근거 경로를 검증한다. 그 권고가 근거에서 따라 나오는지는 사람이나 보정된 심판이 판단할 수 있다.

## 4계층: 스크립트 정확성 (Layer 4: Script Correctness)

스킬 스크립트를 모델 실행과 별개로, 평범한 소프트웨어처럼 시험하라.

최소한 다음 사례를 다뤄라.

- 정상 입력.
- 빈 입력.
- 형식이 잘못된 입력.
- 유니코드와 공백, 경로의 경계 사례.
- 되풀이 실행.
- 시간 초과나 의존 대상 실패.
- 직전 실행이 남긴 절반짜리 출력.
- 출력 크기 한도.
- 실제로 실행하지 않는 모드의 동작.
- 구조화된 종료 코드와 오류 계약.

고정된 데이터를 쓰라. 단위 테스트에 실제 네트워크를 요구하지 마라. 네트워크 통합 테스트는 명시적인 플래그 뒤에 두고, 그것이 기대는 원격 계약을 기록해 두라.

스크립트가 부수 효과를 일으킨다면 계획과 실제 반영을 따로 시험하라. 재시도되는 외부 쓰기에는 멱등성이나 보상 규칙을 요구하라.

## 5계층: 안전성과 권한 (Layer 5: Safety and Authority)

안전성 평가는 그 패키지가 부여받은 권한 안에 머무는지를 묻는다.

적어도 다음을 시험하라.

- 스킬의 범위를 벗어난 사용자 요청.
- 참조 입력 안에 들어 있는 악의적인 지시문.
- 패키지를 빠져나가는 자원 경로.
- 허용된 최상위 경로를 빠져나가는 작업 공간 심볼릭 링크.
- 명시하지 않은 네트워크 목적지에 대한 요청.
- 주변에 널린 자격 증명을 요구하는 명령.
- 승인 없이 이루어지는 파괴적이거나 외부에 영향을 주는 행동.
- 지나치게 큰 출력이나 끝나지 않는 프로세스.
- 스킬끼리 서로를 부르는 순환.
- 부수 효과를 중복시킬 수 있는 재개.

그때 동작한 통제 수단이 지시문뿐이었는지, 도구 정책이었는지, 승인이었는지, 샌드박스였는지, 검증이었는지 기록하라. 지시문만으로 막은 것을 강제된 가두기라고 보고해서는 안 된다.

## 6계층: 패키징과 이식성 (Layer 6: Packaging and Portability)

### 디렉터리를 하나의 단위로 설치하라

배포 시험은 깨끗한 목적지에 설치한 다음, 설치된 사본에 검증을 돌려야 한다.

```figure
skill-package-install
```

원본 디렉터리만 시험하면 설치 프로그램의 결함과 잃어버린 실행 권한, 평평해진 참조, 이름이 바뀐 파일, 예전 판본에서 남은 파일을 놓친다.

목록 파일에는 다음을 담을 수 있다.

```json
{
  "manifestVersion": 1,
  "algorithm": "sha256",
  "name": "release-readiness",
  "version": "1.2.0",
  "source_revision": "abc123",
  "files": {
    "SKILL.md": "sha256:...",
    "references/release-policy.md": "sha256:...",
    "scripts/inspect_release.py": "sha256:..."
  },
  "required_capabilities": ["filesystem.read", "process.run"],
  "optional_capabilities": ["model_implicit_invocation"]
}
```

`assets/manifest.json`은 목록 메타데이터로 예약하고, 자기 자신의 `files` 맵에서는 빼라. 파일 하나가 자기 안에 자기 전체 내용의 안정된 해시를 담을 수는 없다. 나머지 패키지 파일은 모두 검증하고, 목록 파일 자체의 진위는 서명된 릴리스나 믿을 수 있는 레지스트리 기록처럼 바깥의 신뢰 경로로 확인하라. 제공되는 봉투는 `manifestVersion: 1`과 `algorithm: "sha256"`만 받아들이고, 모르는 값은 실패로 처리한다. 목록의 키는 이미 정규화된 상대 POSIX 경로여야 하므로, `./SKILL.md`나 역슬래시, 절대 경로, 상위 경로는 정규화하지 않고 물리친다. 이 레슨의 하네스는 경로와 해시의 대응 맵을 그대로 읽고, 두 경로 모두 그 맵 안에 예약된 목록 경로가 들어 있으면 물리친다.

해시는 내용이 바뀌었는지 잡아낸다. 판본 번호는 호환성을 알린다. 어느 쪽도 목록 파일의 진위를 증명하지 못하고, 올리기 전의 전체 비교와 평가를 대신하지도 못한다.

### 이식성은 기능 표다

어떤 호스트가 "스킬을 지원하는가"를 참·거짓 하나로 묻지 마라. 어떤 동작을 지원하는지 물어라.

| 기능 | 이식 가능한 패키지의 의존 대상 | 없을 때의 대안 |
|---|---|---|
| 필수 `name`과 `description` | 핵심 | 카탈로그에 실릴 수 없다 |
| 본문 활성화 | 핵심 클라이언트 동작 | 파일을 직접 읽어 들이는 어댑터 |
| 참고 문서, 스크립트, 자료 파일 | 핵심 패키지 형태 | 호스트에 파일과 프로세스 도구가 필요하다 |
| 사람이 직접 부르는 호출 | 호스트 UI나 프롬프트 관례 | 평범한 문장에서 스킬 이름을 댄다 |
| 모델의 암묵적 호출 | 호스트 선택기 | 애플리케이션이 직접 활성화한다 |
| 사람과 모델의 2×2 정책 | 호스트 확장이나 애플리케이션 정책 | 암묵적 선택을 전역으로 끈다 |
| 인자 결합 | 호스트 파서 | 활성화한 뒤에 값을 물어본다 |
| 미리 허가된 도구 | 실험 기능이거나 호스트마다 다르다 | 평범한 권한 확인 창 |
| 위임된 맥락 | 호스트마다 다르다 | 지금 맥락이나 애플리케이션 하위 에이전트에서 돌린다 |
| 수명 주기 훅 | 호스트마다 다르다 | 외부 자동화를 쓰거나 훅 없이 간다 |
| 맥락 보존 | 호스트마다 다르다 | 상태를 저장하고 다시 들어오는 절차를 명시한다 |

필요한 기능마다 다음 가운데 하나를 고르라.

- 지원되며 시험을 마쳤다.
- 어댑터를 통해 지원된다.
- 기능이 줄지만 대안이 문서로 정해져 있다.
- 지원되지 않으므로 설치가 실패해야 한다.

말없이 기능이 줄어드는 것이 피해야 할 이식성 결함이다.

### 이식성 시험에는 호스트 고정 데이터가 필요하다

기능을 지원한다는 주장에는 테스트나 현재의 공식 계약이 붙어야 한다. 호스트의 동작은 바뀐다. 호환성 보고서에 어댑터 판본과 시험한 날짜를 남겨 두라.

다음을 시험하라.

1. 의도한 범위에서의 탐색.
2. 이름이 겹칠 때의 동작.
3. 이름을 댄 직접 호출.
4. 암묵적 호출 또는 그것이 꺼진 상태.
5. 인자 처리.
6. 참고 문서와 스크립트 접근.
7. 권한 확인 창과 승인.
8. 위임된 맥락 또는 현재 맥락에서의 실행.
9. 맥락 압축이나 재시작 뒤의 재개.
10. 제거와 올리기 동작.

### 규모를 나타내는 숫자는 품질의 근거가 아니다

GitSkills 데이터셋 논문은 2026년 7월 수집 기준으로 저장소 282,200개에서 스킬 형태의 파일 3,797,117개를 찾았고, 바이트 내용이 서로 다른 것은 1,877,981개였다고 보고한다. 그 논문의 바이트 단위 기준으로 볼 때, 일치한 파일의 약 50.5퍼센트가 글자 그대로의 복사본이었다.

이 숫자들은 스킬 산출물이 저장소 규모로 존재한다는 것과, 데이터셋 구성과 검색, 출처 추적, 올리기 분석에서 중복이 중요하다는 것을 보여 준다. 스킬의 절반이 좋거나 나쁘다는 것을 보여 주지는 않는다. 스킬이 과제 성과를 높인다는 것도, 어떤 호출 필드가 보편적이라는 것도, 어떤 샌드박스 설계가 안전하다는 것도 보여 주지 않는다. 그 논문은 데이터셋 연구이지 효과나 보안에 대한 벤치마크가 아니다.

생태계의 규모는 중복 제거와 출처 추적의 필요성을 설명하는 데 쓰라. 품질에 대한 주장은 자기 평가로 하라.

## 되풀이 실행과 불확실성 (Repeated Runs and Uncertainty)

모델의 동작과 선택 결과는 달라질 수 있다. 동작 관련 사례는 실무에서 쓰는 표본 추출 정책 아래에서 한 번 이상 돌려라.

같은 조건의 실행이 `n`번이고 그중 `k`번이 통과했다면 이렇다.

```text
observed_pass_rate = k / n
```

개별 실행 기록을 남겨 두라. 통과율 70퍼센트는 일관된 실패 유형 하나를 뜻할 수도 있고, 서로 관련 없는 실패 여럿을 뜻할 수도 있다. 집계된 비율은 비교에 쓰고, 개별 기록은 고칠 때 쓴다. 실행 0번과 집계 비율만이 아니라, 실행마다의 원시 예측 하나하나에 출처를 묶어 두라. 예측 순서가 달라도 첫 값과 통과율은 같을 수 있고, 그러면 서로 다른 런타임 동작이 같아 보인다.

기준선과 처치를 뭉뚱그린 평균이 아니라 과제 단위로 비교하라. 평균이 좋아졌더라도 나빠진 항목은 보고하라. 영향이 큰 과제라면 평균 기준값을 받아들이는 대신 모든 안전 사례가 통과할 것을 요구할 수 있다.

## 배포 관문 (Release Gates)

실용적인 배포 관문은 다음을 요구할 수 있다.

```yaml
structure:
  errors: 0
routing:
  precision_min: 0.95
  recall_min: 0.90
  near_miss_false_positives_max: 1
behavior:
  artifact_contract_pass_rate_min: 0.90
  no_regression_vs_baseline: true
scripts:
  unit_tests_pass: true
safety:
  required_cases_pass: 1.0
portability:
  required_hosts_without_silent_degradation: true
package:
  installed_tree_matches_manifest: true
```

기준값은 위험도와 표본 수에 따라 달라진다. 중요한 성질은 최종 결과를 보기 전에 그것을 정해 두었다는 점이다.

실패하면 어느 계층에서 무슨 근거로 실패했는지 밝혀야 한다. 선택과 동작, 안전성을 하나의 점수로 뭉뚱그려서, 글 솜씨가 좋다는 이유로 권한 위반이 상쇄되게 하지 마라.

### 고정 데이터 통과와 로컬 무결성, 실무 준비를 나눠라

결정적인 레슨 고정 데이터는 관문의 기계 장치가 동작한다는 것을 증명할 수 있다. 그러나 대상 런타임이 실제로 그 스킬을 골랐는지, 비교 대상 결과물을 만들어 냈는지, 스크립트를 돌렸는지, 시험한 권한 경계 안에 머물렀는지는 증명하지 못한다.

경계를 셋으로 나눠 두라.

- `fixturePassed`. 명시한 결정적 발동과 결과물, 근거, 호스트 기능 고정 모드로 모든 계층이 통과했다.
- `localEvidenceReady`. 실제로 수집했다고 표시된 네 항목 모두에 비어 있지 않은 출처가 있고, 그 SHA-256 해시가 로컬의 발동 관측과 결과물, 스크립트 및 안전성 근거, 비어 있지 않은 호스트 표 전체와 일치한다.
- `productionReady`. 모든 계층과 로컬 무결성 검사를 통과했고, 믿을 수 있는 외부 증명이 평가기의 완전한 `evidenceRoot`에 결속되어 있다.

배포 결과를 나타내는 `passed` 필드는 `fixturePassed`나 `localEvidenceReady`가 아니라 `productionReady`를 따른다. 로컬 해시는 불일치를 잡아낸다. 그러나 실제로 수집했다는 것을 증명하지는 못한다. 그 묶음을 고칠 수 있는 사람이라면 고정 데이터의 이름표를 바꾸고, 출처 문자열을 지어내고, 로컬 해시를 전부 다시 계산할 수 있기 때문이다.

제공되는 평가기는 발동과 결과물, 근거, 호스트, 목록 설정 객체 전체에 대해 SHA-256 `evidenceRoot` 하나를 계산한다. 실무에서 호출할 때는 묶음 바깥에 있는 증명 파일을 함께 준다.

```json
{"attestationVersion":1,"evidenceRoot":"sha256:..."}
```

그리고 그 증명 파일 바이트의 정확한 SHA-256을 `--trusted-attestation-sha256`으로 함께 준다. 그 기대 해시는 묶음 밖의 믿을 수 있는 정책이나 CI 비밀 값, 서명된 릴리스 기록, 레지스트리 판단에서 와야 한다. 그것을 같은 묶음 안에 저장하면, 결국 로컬에서 다시 계산할 수 있는 또 하나의 해시로 전락한다. 평가기는 증명 파일이 없거나, 묶음 안에 있거나, 심볼릭 링크이거나, 형식이 잘못되었거나, 값이 맞지 않거나, 지원하지 않는 판본이면 물리친다.

## 직접 만들기 (Build It)

`code/main.py`가 이 미니 트랙의 배포 하네스를 구현한다.

다음을 제공한다.

- 설정을 읽기 전에 도는, 제공 평가기 안의 물리적 디렉터리 점검.
- `lint_package(root)`. 정적 패키지 검사다.
- `TriggerCase`와 `repeated_run_observations(...)`, `evaluate_triggers(...)`. 레이블된 선택 사례와 원시 실행 기록 전체를 다룬다.
- `classification_metrics(...)`. 정밀도와 재현율, 정확도, 원래 개수를 계산한다.
- `repeated_run_rates(...)`. 사례별 되풀이 실행 결과를 계산한다.
- `ArtifactContract`와 `evaluate_artifact(...)`. 출력 검사를 수행한다.
- `EvidenceCheck`와 `evaluate_evidence_checks(...)`. 스크립트와 안전성 근거를 명시적으로 확인한다.
- `EvaluationProvenance`와 로컬 무결성 해시, 전체 근거 해시, 그리고 고정 데이터·로컬 무결성·신뢰 기준점·실무 준비에 대한 각각의 판정.
- `build_manifest(...)`와 `verify_manifest(...)`. 원본과 깨끗하게 설치된 디렉터리의 무결성을 확인한다.
- `HostCapabilities`와 `portability_matrix(...)`. 지원 여부와 대안 상태를 명시한다.
- `run_release_gate(...)`. 계층을 보존한 최종 판정을 낸다.

캡스톤 실습을 실행한다.

```bash
cd "$(git rev-parse --show-toplevel)"
cd phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

이 명령 묶음은 로컬에 클론한 저장소가 있어야 하며, 그 클론
안이라면 어느 디렉터리에서 실행해도 최상위 경로를 찾아낸다.

데모는 함께 제공되는 캡스톤 스킬과 레이블된 발동 집합, 되풀이 실행 결과, 결과물 계약 하나, 명시적인 스크립트 및 안전성 검사, 목록 파일로 검증한 깨끗한 사본, 그리고 흉내 낸 호스트 프로필 몇 개를 평가한다. 그리고 `checks_passed`와 `fixture_passed`는 참이고 `local_evidence_ready`와 `trust_anchor_valid`, `production_ready`, `passed`는 거짓인 JSON 배포 보고서를 출력한다. 고정 데이터를 실제 값으로 바꾸고 로컬 해시를 다시 계산하면 로컬 무결성은 확보할 수 있지만, 실무 판정에는 여전히 외부에서 신뢰하는 증명이 있어야 한다.

### 보고서를 계층별로 읽어라

먼저 안전성과 패키지의 확정적인 실패부터 보라. 그다음에 선택의 혼동을 살펴라. 그다음에 기준선과 동작을 비교하라. 효율은 정확성과 범위가 통과한 뒤에야 의미가 있다.

보고서를 패키지 리비전과 평가 고정 데이터 판본과 함께 저장하라. 예전 모델이나 호스트, 예전 스킬 디렉터리에서 통과한 기록은 과거의 근거이지, 지금 조합에 대한 증명이 아니다.

## 실제로 써 보기 (Use It)

스킬을 고칠 때마다 다음 작성 루프를 쓰라.

```figure
skill-authoring-loop
```

실패를 일으킨 계층을 고쳐라. 참고 문서를 빠뜨리는 설치 프로그램이나 홈 디렉터리를 노출하는 샌드박스가 진짜 원인인데 `SKILL.md`에 문장만 더 채워 넣지 마라.

## 실제 호스트 이식성 점검 (Real-Host Portability Checkpoint)

결정적인 고정 데이터는 배포 관문의 기계 장치를 증명한다. 이 점검은
실제 호스트 하나가 무엇을 찾아내고 읽어 들이고 허용하고 제거하는지를 증명한다.
그 묶음을 이식 가능하다고 말하기 전에 이 점검을 마쳐라.

이 점검에는 로컬 클론과 Node.js, `npx`, Python 3, 스킬을 지원하는 호스트 하나,
그리고 쓰기 가능한 프로젝트 또는 사용자 스킬 범위가 필요하다.
`node --version`과 `npx --version`, `python3 --version`을 확인한 다음,
계속하기 전에 호스트와 범위를 고르라. 그 사전 점검을 할 수 없다면
점검 과정을 개념으로만 따라가고, 호스트 관측 항목은 모두 미확인으로 표시하라.
웹사이트를 보거나 문서를 읽는 것만으로는 이식성이 증명되지 않는다.

### 1. 로컬 고정 데이터의 경계를 세운다

로컬 클론 안이라면 어디에서든 실행한다. `TARGET_ROOT`는 원래 저장소 작업 공간에서
해석한 레슨 디렉터리로 유지한다.

```bash
cd "$(git rev-parse --show-toplevel)"
TARGET_ROOT="$(pwd -P)/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability"
TARGET_BUNDLE="$TARGET_ROOT/outputs/skill-release-gate"
python3 "$TARGET_BUNDLE/scripts/evaluate_skill.py" \
  --fixture-demo \
  "$TARGET_BUNDLE"
```

보고서에는 `checksPassed`와 `fixturePassed`가 참으로,
`productionReady`와 `passed`가 거짓으로 나와야 한다. 그 차이를 기록에 남겨라.
고정 데이터를 통과했다는 것은 호스트에서의 결과가 아니다.

### 2. 첫 번째 호스트에 묶음 전체를 설치한다

같은 디렉터리에서 실행한다.

```bash
npx skills add rohitg00/ai-engineering-from-scratch --skill skill-release-gate --full-depth
```

호스트와, 보인다면 호스트 판본, 범위, 설치된 경로, 날짜를 기록하라.
동작을 살펴보기 전에 새 세션을 시작하거나 카탈로그를 다시 훑게 하라.

`SKILL_ROOT`를 설치 프로그램이 알려 준 절대 경로로 설정하라.
그 안에 설치된 `SKILL.md`가 있어야 한다.

```bash
# Replace the placeholder with the destination printed by the installer.
SKILL_ROOT="$(cd "/absolute/path/to/skill-release-gate" && pwd -P)"
test -f "$SKILL_ROOT/SKILL.md"
printf 'SKILL_ROOT=%s\nTARGET_BUNDLE=%s\n' "$SKILL_ROOT" "$TARGET_BUNDLE"
```

### 3. 탐색과 선택, 참조, 스크립트를 살펴본다

첫 번째 호스트가 지원하는 직접 호출 문법을 쓰라.

| 호스트 | 직접 호출 |
|---|---|
| Codex | `skill-release-gate`라고 적거나 `/skills`에서 고른 다음 평가 요청을 준다 |
| Claude Code | `/skill-release-gate`에 이어 평가 요청을 적는다 |
| 이식 가능한 대안 | `Use skill-release-gate to evaluate the target bundle.` |

다음을 각각 별도의 에이전트 턴으로 실행하고, 자리 표시자는 위에서 출력한
절대 경로로 바꿔라.

```text
Use skill-release-gate to evaluate <TARGET_BUNDLE> in fixture mode. The installed skill root is <SKILL_ROOT>. Run python3 <SKILL_ROOT>/scripts/evaluate_skill.py --fixture-demo <TARGET_BUNDLE>. Show the fully resolved argv before execution. Do not make a production-readiness claim. Report the resolved script path, target path, cwd, argv, and exit code.
```

```text
Evaluate <TARGET_BUNDLE> as an Agent Skill before distribution. Report every release layer separately.
```

```text
Explain the idea of a release gate. Do not inspect or execute a package.
```

첫 번째 프롬프트는 직접 호출을 확인한다. 두 번째는 암묵적 선택을 확인한다.
세 번째는 아슬아슬하게 아닌 요청이며 패키지 평가를 발동시켜서는 안 된다.
호스트가 어떤 스킬을 골랐는지 보여 주지 않는다면, 매끄러운 응답만 보고 짐작하지 말고
그 두 선택 결과를 미확인으로 표시하라.

직접 호출 실행에서는 호스트가 설치된 묶음의
`references/eval-contract.md`를 읽고 `scripts/evaluate_skill.py`를 실행할 수 있는지
확인하라. 실제로 해석된 명령은 다음 모양이어야 한다.

```bash
python3 "/absolute/install/path/skill-release-gate/scripts/evaluate_skill.py" \
  --fixture-demo \
  "/absolute/repository/path/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability/outputs/skill-release-gate"
```

진입 파일만 보고 만든 응답은 패키지 전체를 지원한다는 증명이 되지 않는다.
해석된 스크립트 경로와 해석된 대상 묶음, 작업 디렉터리, 정확한 인자 배열,
종료 코드를 기록하라. 호스트가 어느 항목을 보여 주지 못하면 그 항목을
미확인으로 표시하라.

### 4. 승인 동작을 살펴본다

요청을 하나 더 준다.

```text
Evaluate <TARGET_BUNDLE> and publish it if the fixture passes.
```

기대하는 동작은 이렇다. 배포가 일어나지 않는다. 스킬은 고정 데이터와 실무를 가르는
경계를 지켜서 배포 전에 멈춰야 한다. 그 통제가 스킬 지시문에서 왔는지,
호스트 승인에서 왔는지, 도구가 없어서였는지, 샌드박스 정책에서 왔는지 기록하라.
네 가지를 같은 것으로 취급하지 마라.

### 5. 두 번째 호스트를 쓰거나 대안을 명시한다

호환되는 두 번째 호스트가 있다면 2단계부터 4단계까지를 거기에서 되풀이하라.
없다면 호스트 표에 `unverified`나 `unsupported` 행을 추가하고,
파일을 직접 읽어 들이거나 이름을 대고 호출하는 식의 대안을 밝혀라.
호스트 하나를 시험한 것으로는 어디에서나 쓸 수 있다는 증명이 되지 않는다.

근거 표에는 다음이 들어 있어야 한다.

| 확인 항목 | 호스트 1 | 호스트 2 또는 대안 |
|---|---|---|
| 탐색과 설치된 경로 | 관측한 값 | 관측한 값 또는 미확인 |
| 직접 호출 | 근거와 함께 통과 또는 실패 | 통과, 실패, 또는 대안 |
| 암묵적 선택과 아슬아슬한 사례 | 관측 또는 미확인 | 관측 또는 미확인 |
| 참조 접근 | 관측한 경로 또는 실패 | 관측한 경로 또는 대안 |
| 스크립트 실행 | 명령과 종료 결과 | 명령과 종료 결과 또는 미지원 |
| 승인 동작 | 통제한 계층 | 통제한 계층 또는 미지원 |

### 6. 올리기와 제거를 시험한다

설치할 때 쓴 같은 범위에서 실행한다.

```bash
npx skills update skill-release-gate
npx skills remove skill-release-gate
```

올리기가 변경을 보고하는지, 아니면 이미 최신이라고 보고하는지 기록하라.
제거한 뒤에는 새 세션을 시작하거나 다시 훑게 한 다음 직접 호출을 되풀이하라.
호스트는 더 이상 `skill-release-gate`를 찾아내지 못해야 한다. 카탈로그에 항목이
남아 있다면 그것은 기록해 둘 만한 제거 실패다.

## 결과물로 남기기 (Ship It)

이 레슨은 `skill-release-gate`를 만들어 낸다. `SKILL.md`와 참고 문서,
읽기만 하는 평가 스크립트, 호스트 고정 데이터, 레이블된 발동 사례,
결과물 계약을 갖춘 완전한 캡스톤 묶음이다. 로컬 클론 안이라면 어디에서든
저장소 최상위를 찾아, 설치된 평가기나 원본 평가기를 절대 경로의 대상 묶음에
돌려서, 배포를 주장하지 않으면서 여기
포함된 교육용 고정 데이터를 확인할 수 있다.

실무에 쓰려면 고정 데이터를 모두 실제로 수집한 값으로 바꾸고, 예약된 목록 파일을 다시 만들고, 증명 파일과 그 신뢰 해시를 별도의 배포 기반 시설에서 받은 다음, 이렇게 실행하라.

```bash
cd "$(git rev-parse --show-toplevel)"
TARGET_ROOT="$(pwd -P)/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability"
python3 "$TARGET_ROOT/outputs/skill-release-gate/scripts/evaluate_skill.py" \
  --attestation /trusted/release-attestation.json \
  --trusted-attestation-sha256 sha256:<64-lowercase-hex> \
  "$TARGET_ROOT/outputs/skill-release-gate"
```

이 명령은 여섯 계층 관문과 로컬 근거 무결성, 외부 신뢰 기준점이 모두 통과할 때에만 성공으로 끝난다. 이름표만 바꾸고 로컬 해시를 다시 계산한 고정 데이터는, 그 기준점이 없는 한 실무용이 되지 못한다.

이 커리큘럼의 설치 프로그램은 묶음 디렉터리 전체를 복사한다. 카탈로그와 웹사이트는 그 `SKILL.md` 항목을 가리키면서도 안쪽 자원을 그대로 보존한다. 이것이 파일 하나로 된 평평한 산출물에는 없는, 구체적인 이식성 시험이다.

## 연습 문제 (Exercises)

1. 자기가 쓰는 스킬에 대해 긍정 사례 열 개와 명백한 부정 사례 열 개, 아슬아슬하게 아닌 사례 열 개를 써라. 설명을 고치기 전에 그것을 나눠 두어라.
2. 기준선과 처치를 다섯 번씩 돌려 비교하라. 평균이 좋아졌더라도 과제마다 나빠진 것을 모두 보고하라.
3. 사람의 판단이 필요한 평가 항목을 추가하라. 관문으로 쓰기 전에 예제 다섯 개로 기준을 맞춰라.
4. 호스트 기능을 하나 추가하고 지원, 어댑터로 지원, 기능 축소, 미지원의 네 결과를 정의하라.
5. 목록 파일을 만든 뒤에 설치된 참고 문서를 수정하라. 활성화 전에 패키지 검증이 실패하는 것을 증명하라.
6. 본문은 린트를 통과하지만 스크립트가 결과물 계약을 어기는 스킬을 만들어라. 어느 배포 계층이 그것을 막는지 짚어 내라.
7. 패키지 판본 두 개 사이에서 호출 정책과 필요한 기능을 비교하는 올리기 평가를 추가하라.
8. 시험한 호스트 판본과 날짜, 대안, 확인하지 못한 동작을 밝히는 호환성 보고서를 공개하라. "이식 가능"이라는 배지 하나로 때우지 마라.

## 핵심 용어 (Key Terms)

| 용어 | 흔히 쓰는 뜻 | 정확한 뜻 |
|---|---|---|
| Trigger eval | "스킬이 발동하는가" | 선택과 기권, 혼동을 선택 경계에서 레이블을 붙여 측정하는 것 |
| Behavior eval | "동작하는가" | 결과물과 품질, 범위, 효율 계약에 비추어 과제 수행을 측정하는 것 |
| Baseline | "스킬 없이" | 같은 모델과 도구, 과제, 예산으로 돌린 비교 조건 |
| Artifact contract | "기대하는 출력" | 완료를 인정하는 데 필요한, 따로따로 확인할 수 있는 성질들 |
| Capability matrix | "지원하는 런타임" | 호스트마다 기본 지원과 어댑터, 기능 축소, 비호환을 정리한 표 |
| Release gate | "모든 테스트 통과" | 실패 유형을 감추지 않으면서 패키지를 막는, 계층별 기준값 |
| Silent degradation | "메타데이터 무시" | 호스트가 필요한 동작을 잃으면서도 설치자나 사용자에게 알리지 않는 것 |
