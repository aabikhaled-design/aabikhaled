# 스킬 탐색과 점진적 공개 (Skill Discovery and Progressive Disclosure)

> 스킬은 본문이 읽히기 전에 이미 쓸모를 갖는다. 이름과 설명이 카탈로그에 실릴 자격을 얻고, 더 깊은 파일들은 작업이 거기에 닿았을 때에야 맥락에 들어갈 자격을 얻는다.

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 13 · 22 (Agent Skills: Portable Contract and Runtime Boundary)
**Time:** ~105 minutes

## 학습 목표 (Learning Objectives)

- 적용 범위와 검증, 이름 충돌 정책, 카탈로그 공개를 각각 분리한 파일 시스템 탐색 파이프라인을 만든다.
- 공개의 세 단계를 설명한다. 카탈로그 메타데이터와 활성화된 지시문, 그리고 작업에 필요한 자원이다.
- 에이전트가 패키지 전체를 읽지 않고도 필요한 세부 내용에 바로 닿을 수 있도록 참조를 설계한다.
- 카탈로그가 쓰는 공간을, 활성화된 스킬이 쓰는 맥락과 따로 예산으로 잡는다.
- 스킬이 자기 자원을 읽을 때 경로를 거슬러 올라가거나 심볼릭 링크로 밖으로 빠져나가는 것을 막는다.

## 문제 (The Problem)

에이전트에 설치된 스킬이 200개라고 하자. 세션을 시작할 때 모든 `SKILL.md`와 참고 파일, 스크립트, 템플릿을 읽어 들이면 지금 할 일이 관련 없는 절차에 파묻힌다. 반대로 아무것도 읽지 않으면 사용자가 정확한 파일 경로를 외우고 있어야 한다.

흔히 쓰는 절충안은 카탈로그다. 자격을 갖춘 스킬마다 간결한 신원과 언제 쓰는지에 대한 설명만 모델에 보여 주고, 실제 본문은 그 스킬이 선택된 뒤에 읽어 들인다. 그런데 여기에서 새로운 문제가 둘 생긴다.

첫째, 탐색은 파일을 재귀적으로 찾는 일이 아니다. 스킬은 프로젝트나 사용자, 관리자, 플러그인, 런타임 내장 가운데 어느 범위에나 있을 수 있다. 패키지 두 개가 같은 이름을 쓸 수도 있다. 심볼릭 링크가 믿을 수 있는 경로 밖을 가리킬 수도 있다. 형식이 잘못된 패키지가 카탈로그 공간을 잡아먹거나, 아예 호출할 수 없는 상태가 될 수도 있다.

둘째, 점진적 공개가 점진적 혼란이 될 수 있다. `SKILL.md`가 "관련 안내를 읽어라"라고만 적어 두었는데 패키지에 안내 문서가 열두 개라면, 모델은 짐작해야 한다. 그리고 안내마다 다시 세 파일을 가리킨다면, 읽어 들이는 일이 끝을 알 수 없는 그래프 순회가 된다.

좋은 런타임은 탐색을 결정적으로 만들고 공개를 의도적으로 만든다.

## 개념 (The Concept)

### 탐색은 컴파일러 파이프라인이다

파일 시스템을 원본 입력으로 다뤄라. 날것의 경로를 모델에 그대로 내주지 마라.

```figure
skill-discovery-pipeline
```

각 단계는 구조화된 데이터와 구조화된 실패를 내놓아야 한다. 탐색 기록은 다음에 답할 수 있어야 한다.

- 어떤 경로를 뒤졌는가?
- 어떤 후보를 찾았는가?
- 어떤 후보를 왜 물리쳤는가?
- 이름이 충돌했을 때 어떤 패키지가 이겼는가?
- 예산 때문에 어떤 카탈로그 항목이 줄거나 빠졌는가?

이런 근거가 없으면 "내 스킬을 모델이 쓰지 않는다"는 문제를 거의 진단할 수 없다.

### 적용 범위는 런타임이 정하는 정책이다

이식 가능한 명세는 스킬 패키지의 형태를 정의할 뿐, 어디에 설치해야 하는지나 어느 쪽이 우선인지를 정하지 않는다. 어디를 뒤질지는 호스트가 정한다.

일반적인 런타임이라면 다음 범위를 쓸 수 있다.

| 범위 | 경로 예시 | 관리 주체 |
|---|---|---|
| 작업 공간 | `<repo>/.agents/skills/` | 프로젝트 관리자 |
| 사용자 | `<user-data>/skills/` | 개발자 한 명 |
| 관리자 | `<system>/skills/` | 기계나 조직의 정책 |
| 플러그인 | 서명된 플러그인 묶음 | 플러그인 발행자와 설치자 |
| 내장 | 런타임 패키지 | 런타임 제공자 |

2026년 8월 기준으로 Codex는 `$CWD/.agents/skills`에서 시작해 상위 디렉터리를 거쳐 저장소 최상위까지 프로젝트 범위를 뒤지고, 그와 함께 사용자와 관리자, 내장 위치를 뒤진다고 문서에 적어 두었다. 심볼릭 링크로 연결된 스킬 디렉터리도 지원한다. 이름이 같은 경우 하나로 합치지 않고 둘 다 나타날 수 있다. 이것은 Codex의 동작이지 `SKILL.md`가 요구하는 사항이 아니다. 어댑터를 만들 때는 현재의 [Codex 스킬 문서](https://learn.chatgpt.com/docs/build-skills)를 직접 확인하라.

디렉터리 이름을 보고 우선순위를 지어내지 마라. 정책으로 명시하고 시험하라. 이 레슨의 실습은 `Scope`마다 정수 순위를 명시해서, 같은 후보 집합이면 언제나 같은 결과가 나오게 한다.

### 이름 충돌에는 `name` 이상의 신원이 필요하다

`release-readiness`라는 이름의 패키지가 둘 있는 것은 정당할 수 있다. 하나는 작업 공간에서 덮어쓴 것이고 다른 하나는 사용자 기본값일 수 있다. 그래서 카탈로그 항목에는 적어도 다음이 필요하다.

```json
{
  "name": "release-readiness",
  "description": "Inspect a release candidate for this repository.",
  "scope": "workspace",
  "source": "/repo/.agents/skills/release-readiness",
  "selected": true
}
```

흔히 쓰는 충돌 정책은 이렇다.

| 정책 | 이점 | 위험 |
|---|---|---|
| 모든 후보를 남긴다 | 감춰지는 것이 없다 | 모델이 모호한 이름들을 보게 된다 |
| 우선순위가 높은 범위가 이긴다 | 호출이 단순해진다 | 로컬 패키지가 믿을 만한 패키지를 가릴 수 있다 |
| 중복을 물리친다 | 조용히 가려지는 일이 없다 | 정당한 덮어쓰기가 동작하지 않게 된다 |
| 출처로 이름을 한정한다 | 신원이 분명해진다 | 사용자에게 보이는 이름이 길어진다 |

호스트마다 정책을 하나 골라라. 그리고 모델 카탈로그에서 빠진 후보라도, 물리쳤거나 가려진 후보를 진단 기록에는 남겨 두어라.

### 공개의 세 단계

Agent Skills 명세는 단계적으로 읽어 들이는 방식을 기술한다. 핵심은 단계마다 목적이 다르다는 점이다.

```figure
skill-disclosure-levels
```

#### 1단계: 카탈로그 메타데이터

모델에는 그 스킬을 이웃한 스킬들과 구별할 만큼의 정보가 필요하다. 명세는 카탈로그 항목 하나에 대략 100토큰을 잡지만, 실제로 어떻게 직렬화하고 토큰화할지는 호스트의 몫이다.

쓸모 있는 설명에는 절이 둘 있다.

```yaml
description: Validate a release candidate and produce a readiness report. Use when the user asks whether a version, tag, or package is ready to publish.
```

앞 절은 그 스킬이 무엇을 할 수 있는지 말한다. 뒤 절은 언제 발동해야 하는지의 경계를 말한다. 25번 레슨은 발동해야 하는 요청과 아슬아슬하게 아닌 요청으로 그 경계를 평가한다.

#### 2단계: 활성화된 지시문

활성화된 뒤의 본문은 지도이자 절차여야 한다. 명세는 `SKILL.md`를 500줄 아래로 유지하라고 권한다. 그것은 설계상의 신호이지, 그만큼 채우라는 목표가 아니다.

본문에는 다음이 들어가야 한다.

- 작업의 경계.
- 기본 절차.
- 갈라지는 조건.
- 더 깊은 파일에 대한 직접 참조.
- 도구와 스크립트의 계약.
- 실패했을 때와 멈출 때의 동작.
- 기대하는 결과물과 그것을 확인하는 방법.

진입 파일을 짧게 만들려는 이유만으로 중심 절차를 참고 문서로 옮기지 마라. 활성화되는 순간 모델이 제대로 시작할 만큼의 맥락이 있어야 한다.

#### 3단계: 보조 자원

참고 문서는 설명이나 데이터를 준다. 스크립트는 결정적인 계산을 준다. 자료 파일은 지시문이 아니라, 복사하거나 채우거나 변환해서 결과물로 만드는 것이다.

| 디렉터리 | 모델이 읽는가? | 모델이 실행하는가? | 흔히 담기는 것 |
|---|:---:|:---:|---|
| `references/` | 필요할 때 읽는다 | 아니다 | 스키마, 정책, 분야별 안내 |
| `scripts/` | 들여다볼 수 있다 | 허용된 도구를 통해서만 | 검증기, 변환기, 수집기 |
| `assets/` | 쓸모가 있을 때만 | 아니다 | 템플릿, 고정 데이터, 이미지, 시작용 파일 |

이 이름들은 관례일 뿐 어떤 마법 같은 기능이 아니다. 호스트에는 여전히 파일 접근 권한과 실행 도구가 있어야 한다.

### 주제별로 몰아넣기보다 분기별 참조가 낫다

진입 파일을 판단 지도처럼 써라.

```markdown
## Choose the path

- For a Python package, read `references/python-release.md`.
- For a container image, read `references/container-release.md`.
- For a documentation-only release, read `references/docs-release.md`.
- If the release combines artifact types, read only the guides for those artifacts.
```

이렇게 하면 참고 문서마다 언제 읽어야 하는지가 눈에 보이는 조건으로 붙는다. "더 알고 싶으면 `references/`를 읽어라"는 그러지 못한다.

참조 그래프를 얕게 유지하라. 공식 지침은 `SKILL.md`에서 바로 연결하고 긴 사슬을 피하라고 권한다. 한 단계만 건너면 닿을 수 있어야 도달 가능성을 시험할 수 있고, 꼭 필요한 제약이 맥락에 끝내 들어오지 못하는 일도 줄어든다.

```figure
skill-reference-map
```

### 카탈로그 예산과 활성 맥락은 서로 다른 예산이다

스킬 `i`의 직렬화된 카탈로그 비용을 `c_i`, 카탈로그 예산을 `B_c`, 활성화된 본문의 비용을 `b_j`, 실제로 읽어 들인 자원을 `r_k`라고 하자.

```text
catalog_cost = sum(c_i for every published skill)
active_cost = sum(b_j for every activated skill) + sum(r_k for every disclosed resource)
```

한쪽 예산을 줄인다고 다른 쪽이 저절로 줄지는 않는다. 설명을 짧게 쓰면 카탈로그 공간은 아끼지만, 활성화된 900줄짜리 본문은 여전히 작업을 파묻는다. 본문을 참고 문서로 쪼개는 것도, 런타임과 지시문이 관련 없는 분기를 실제로 읽지 않을 때에만 활성 비용을 줄여 준다.

Codex는 현재 컨텍스트 윈도 크기를 알 수 있을 때 초기 스킬
목록에 그 2퍼센트를 배정한다. 8,000자라는 값은 그 크기를
모를 때 쓰는 대체값일 뿐이며, 2퍼센트 규칙과 함께
적용되는 두 번째 상한이 아니다. 카탈로그가 해당 예산을
넘으면 설명이 줄거나 항목이 빠질 수 있다. 이 수치는 현재
Codex의 정책이지 Agent Skills 표준의 성질이 아니다.

### 자원 경로는 신뢰 경계다

스킬은 자기 패키지 안의 파일만 읽어야 한다. 문자열 앞부분만 비교하는 것으로는 부족하다.

```text
references/../../../../.ssh/config
references/external-link -> /private/company-secrets
```

패키지의 최상위 경로와 후보 경로를 파일 시스템 규칙대로 해석하고, 절대 경로 입력은 물리치고, 해석된 후보가 해석된 최상위 경로 아래에 남아 있는지 확인하라. 심볼릭 링크를 허용할지는 탐색을 시작하기 전에 정하라. 허용한다면, 링크가 실제로 가리키는 대상을 매번 확인하라.

```figure
skill-resource-containment
```

경로가 갇혀 있다고 해서 내용을 믿을 수 있는 것은 아니다. 패키지 안에 정당하게 들어 있는 참조 문서에도 악의적인 지시문이 담길 수 있다. 그 위협은 26번 레슨에서 다룬다.

### 읽어 들이는 과정이 보여야 한다

비밀 값을 기록하지 않으면서 공개 사건을 남겨라.

```json
{
  "event": "skill.resource.loaded",
  "skill": "release-readiness",
  "resource": "references/python-release.md",
  "reason": "candidate contains pyproject.toml",
  "bytes": 2840
}
```

이유를 남기면 맥락 선택이 검토할 수 있는 근거가 된다. 그리고 에이전트가 "혹시 몰라서" 모든 파일을 읽게 만드는 지시문을 찾아내는 데에도 도움이 된다.

## 직접 만들기 (Build It)

`code/main.py`에서 결정적으로 동작하는 탐색·공개 엔진을 만든다.

탐색 쪽은 다음으로 이루어진다.

- `Scope`. 출처와 우선순위 메타데이터를 담는다.
- `SkillCandidate`. 아직 검증되지 않은 파일 시스템 후보다.
- `discover_scope(scope)`. 바로 아래의 스킬 디렉터리를 훑는다.
- `resolve_collisions(candidates, precedence)`. 명시한 정책 하나를 적용한다.
- `CatalogEntry`와 `build_catalog(...)`. 한도를 지킨 메타데이터를 공개한다.
- `CatalogBudget`. 글자 수가 곧 토큰 수인 척하지 않으면서 직렬화된 항목의 크기를 계산한다.

공개 쪽은 다음으로 이루어진다.

- `load_skill_body(entry, ...)`. 2단계 활성화를 수행한다.
- `validate_reference(skill_dir, reference)`. 경로가 패키지 안에 갇혀 있는지 확인한다.
- `load_reference(...)`. 한도를 지키며 3단계 읽기를 수행한다.

실습을 실행한다.

```bash
cd "$(git rev-parse --show-toplevel)"
cd phases/13-tools-and-protocols/24-skill-discovery-and-progressive-disclosure
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

이 명령 묶음은 로컬에 클론한 저장소가 있어야 하며, 그 클론
안이라면 어느 디렉터리에서 실행해도 최상위 경로를 찾아낸다.

데모는 임시 프로젝트 범위와 사용자 범위를 만들고, 이름 충돌을 하나 넣고, 일부러 작게 잡은 예산 아래에서 카탈로그를 만들고, 스킬 하나를 활성화하고, 정상적인 참조 읽기와 경로를 거슬러 빠져나가려는 시도를 모두 해 본다. 영구적으로 설치되는 파일은 없다.

### 탐색을 얕게 하는 이유

`discover_scope`는 바로 아래 자식 디렉터리에 `SKILL.md`가 있는지만 본다. 안쪽 어디에 있는 `SKILL.md`든 별도 패키지로 취급하며 재귀적으로 파고들지 않는다. 그래야 패키지 경계가 지켜지고, 설치된 스킬 안의 예제나 고정 데이터가 실수로 공개되는 일도 없다.

### 실습이 임의의 YAML을 파싱하지 않는 이유

실습은 카탈로그에 필요한 스칼라 프론트매터만 지원한다. 실무 런타임이라면 스키마를 명시하고 크기 한도를 두고 사용자 정의 객체 생성을 끈, 안전한 YAML 파서를 써야 한다. "표준 라이브러리만 쓴다"는 것은 가르치기 위한 제약이지, YAML의 일부만 흉내 낸 방언을 조용히 지어내도 된다는 허가가 아니다.

## 실제로 써 보기 (Use It)

탐색 어댑터를 만들 때 다음 점검표를 적용하라.

1. 설정된 경로를 모두 나열하고, 각각에 누가 쓸 수 있는지 밝혀라.
2. 심볼릭 링크로 연결된 패키지를 허용할지 정하라.
3. 패키지 이름과 디렉터리 이름, 필수 메타데이터, 진입 본문의 크기를 검증하라.
4. 내부 신원에 출처와 범위를 함께 보존하라.
5. 이름이 겹칠 때의 동작을 명시하고 시험하라.
6. 모델에 실제로 보내는 직렬화된 카탈로그의 크기를 측정하라.
7. 본문이나 자원을 왜 읽어 들였는지 기록하라.
8. 자원 읽기를 해석된 패키지 최상위 경로 안에 가둬라.
9. 참조한 파일이 없으면 분명하게 실패하라.
10. 설치 상태나 정책이 바뀌면 카탈로그를 다시 만들어라.

## 결과물로 남기기 (Ship It)

이 레슨은 `skill-catalog-builder` 묶음을 만들어 낸다. 순서를 명시한 경로들을 훑고, 심볼릭 링크로 된 진입 파일과 이름이 디렉터리와 맞지 않는 경우를 물리치고, 범위를 넘나드는 이름 충돌을 정리하고, 우선순위가 같은 중복은 물리치고, 선택된 메타데이터를 항목 수와 설명 길이, 직렬화된 글자 수의 예산에 맞춰 넣는다.

그 JSON 보고서에는 선택된 항목과 가려진 후보, 빠진 항목, 검증 오류, 우선순위, 예산 사용량이 담긴다. 본문과 참조를 읽어 들이는 일은 별도의 실행 시점 동작으로 남으므로, 카탈로그 생성기는 스크립트를 실행하지도 않고 패키지 전체를 맥락에 들이지도 않는다.

## 연습 문제 (Exercises)

1. 플러그인 범위를 추가하고 사용자 범위와 내장 범위 사이에 우선순위를 두어라. 이름 충돌 결과를 테스트로 증명하라.
2. 충돌 정책을 우선순위 방식에서 이름을 한정하는 방식으로 바꿔라. 두 항목이 모두 카탈로그에 남게 하라.
3. `load_reference`에 바이트 크기 한도를 추가하라. 한도와 정확히 같은 파일과, 1바이트 넘는 파일을 각각 시험하라.
4. 거의 똑같이 들리는 설명 두 개를 만들어라. 그리고 발동 경계가 겹치지 않도록 다시 써라.
5. 모든 참고 문서와 스크립트의 해시를 담은 목록 파일을 추가하라. 자원이 수정되었다면 읽어 들이기 전에 잡아내라.
6. 데모에 계측을 붙여 1단계와 2단계, 3단계의 바이트 수를 따로 보고하게 하라.

## 핵심 용어 (Key Terms)

| 용어 | 흔히 쓰는 뜻 | 정확한 뜻 |
|---|---|---|
| Skill discovery | "SKILL.md를 전부 찾기" | 설정된 범위를 뒤지고, 패키지를 검증하고, 출처를 붙이고, 정책을 적용하는 일 |
| Skill catalog | "설치된 스킬 목록" | 자격을 갖춘 패키지에 대해 모델이 볼 수 있는 간결한 선택용 메타데이터 |
| Collision policy | "중복 가운데 무엇이 이기나" | 출처가 다르면서 이름이 같은 후보들에 대해 명시해 둔 규칙 |
| Progressive disclosure | "지연 로딩" | 카탈로그에서 본문으로, 다시 분기별 자원으로 맥락을 단계적으로 들이는 것 |
| Reference graph | "스킬이 연결한 파일들" | 닿을 수 있는 자원의 구조와 각각을 읽어 들이는 조건 |
| Path containment | "폴더 안에 머물기" | 해석된 자원 경로가 해석된 패키지 최상위 경로 안에 남아 있는지 확인하는 것 |
